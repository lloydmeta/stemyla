# Invariants

The rules the code relies on, one per ID.  `CLAUDE.md` lists them in one line each; this file says why each holds, what enforces it and where it is not yet enforced.  An ID is never reused: a rule that is dropped keeps its heading, marked "Retired", with the reason.

Each rule names its enforcement on an `* Enforced by:` line, where a name in a code span is a test that `docs-check` confirms exists.  "Prose only" means that nothing fails when the rule is broken; those gaps are tracked in `tech-debt.md`.  Reviewers cite these IDs, and quote the rule, when they report a breach.

## Build and repository

### BUILD-1: building and serving is Rust only

Building and serving the app uses only Cargo, Trunk and `xtask serve`.  Never suggest or add Python or another non-Rust server or build step.  Python appears only in `tools/roformer_export.py`, which generates test fixtures from the PyTorch reference.

* Why: one toolchain to install and audit; the maintainer's choice for this repo.
* Enforced by: `no_python_in_the_build` (CI `test` job), over the git index.  It fails a tracked Python file other than `tools/roformer_export.py`.  It fails the words `python`, `pip` or `uv` in CI, Trunk, `build.rs` or Cargo's config.  It fails the name of Python's web server in a tracked text file outside plans, decisions and review logs.  It does not see Rust code outside `build.rs` that starts Python, or a shell script that runs Python.  It also does not see a script with a shebang and no extension, or a server in another language.

### ASSET-1: no audio, stems or model weights in the repo

Never commit audio, stems or model weights.  The model weights have no stated licence: link to them, never host them.

* Why: songs are copyrighted, and the weights carry no licence that allows redistribution.
* Enforced by: `no_audio_or_weights_are_tracked` (CI `test` job), over the git index, and `.gitignore`.  It fails an audio or weight extension, and a file over 1 MiB.  A short clip under another extension passes.  It does not read the history.

### DEPS-1: crates are vetted, young ones pinned, licences listed

Before you add a crate, confirm that it exists and is maintained.  Pin a young crate exactly, with `=`.  A crate below 1.0 is young if its first version on crates.io is under two years old; `SETTLED_CRATES` in `xtask/src/rules.rs` lists the older ones, each with that date.  A crate at 1.0 or later is young if it was recently published, which a person judges.  Take crates from a registry, not from git.  Keep `THIRD-PARTY.md` current.  `THIRD-PARTY.md` covers what ships: the wasm dependency tree of `app`, `stem-worker` and `decode-worker`, generated by the two commands in it.

* Why: supply-chain risk, and the shipped page must credit every licence it bundles.
* Enforced by: `young_crates_are_pinned` and `third_party_lists_what_ships` (CI `test` job).  The first fails a registry requirement that admits a version below 1.0 and is not an `=` pin, unless `SETTLED_CRATES` names the crate.  It also fails a source that is not a registry, such as git.  It does not check an entry's date; a reviewer does.  The second compares both tables of `THIRD-PARTY.md` with their commands.  Neither sees a young crate at 1.0 or later, or whether a crate is maintained.
* Gaps: TD-7.

### LAYER-1: crates depend only downwards

Each workspace crate depends only on the workspace crates that its row in the layers table of `docs/ARCHITECTURE.md` lists, and on `test-support` as a dev-dependency.  This covers dev- and build-dependencies, for every target and feature.  Every path crate in the build is a workspace crate.  No crate from a registry or git has a workspace crate's name, or takes a workspace crate.  Each listed crate is in a lower layer of the table (Test support, Pure, Engine and GPU, Shells, Tools).  `test-support` is a dev-dependency only and takes no workspace crate, and `dsp` does not take it.  The page side (`app` and `decode-worker`) and the worker side (`stem-worker`) meet only through `stem-protocol`.  The workspace crates that `stem-worker` reaches through normal dependencies, for any target, have only `stem-protocol` in common with those that `app` or `decode-worker` reaches.  In the normal dependency tree of the web app (`app`, `decode-worker` and `stem-worker`), `synth` brings no other crate.

* Why: keeps the page from linking the model or the GPU code, and keeps the pure crates testable without a browser.  It keeps `stem-protocol` the one contract between the page side and the worker side.  It also keeps the crates that `synth` needs only for tools and tests out of the web app's build, so `THIRD-PARTY.md`'s first table does not credit them.
* Enforced by: `crates_depend_only_downwards`, `the_page_and_the_worker_meet_only_through_stem_protocol` and `synth_brings_no_crate_into_the_web_app` (CI `test` job).  The first compares the dependencies between workspace crates in `cargo metadata` with the layers table.  It also fails on a crate that hides a dependency from that comparison.  The second follows the normal dependencies from `app`, `decode-worker` and `stem-worker`.  It fails on a workspace crate other than `stem-protocol` that `app` or `decode-worker` shares with `stem-worker`.  Decision 0005 sets how strictly they read the rule.
* Gaps: TD-23.

### DSP-1: dsp is beginner style

`dsp/` has zero dependencies.  It uses only the types `f32`, `usize`, `bool`, `&[f32]`, `&[&[f32]]`, `Vec<f32>` and `Vec<(f32, f32)>`.  It uses only `while`, `for` over a range, `if` and indexing: no iterators, closures or `swap`.  It calls only the methods `len`, `push` and `capacity`.  Write `x = x + y`, `len() > 0` and an `if` for each bound of a clamp.  Do not write a compound assignment (`x += y` and the others), `is_empty` or `clamp`.  `dsp/src/lib.rs` expects each clippy lint that these forms, or a swap written out, trigger.  Each has a reason, and every other lint keeps its workspace level.

* Why: `dsp/` is a first reading exercise in Rust; it must stay readable without knowing the iterator API, or shortcuts such as `+=`, `is_empty` and `clamp`.
* Enforced by: `dsp_is_beginner_style` (CI `test` job), a scan of the tokens in `dsp/` for the likely breaches.  Clippy fails a stale `#![expect]`.
* Gaps: TD-3.

## Memory

### MEM-1: a song- or model-sized buffer is never copied to share it

WebAssembly memory never shrinks, so a copy costs for the rest of the tab's life.  On the storage path, a song's audio stays in its session files: the page and the workers read it in blocks, and make no song-length buffer of it in WebAssembly memory (decision 0015).  The memory path's rules allow exceptions of at most `MEMORY_PATH_MAX_FRAMES` frames, and less for a song with more lanes in memory (`app::memory_path_frames`, decision 0020).  They are the memory path's input (D9 of `plans/active/stream-from-storage-m7.md`) and a stem whose file is not complete (D11).  Classic drums on the page is a third: on both page routes, it makes one mix of its input and its new lane in memory (D8, decision 0020).  Audio in memory (the memory path, the demo song) is `engine::Samples` (an immutable `Arc<Vec<f32>>`; cloning shares it), and slices are borrowed.  A new copy of a song- or model-sized buffer needs a stated reason and a test that pins the sharing (for example `Samples::shares`).

* Why: MEM-4.
* Enforced by: `a_mono_stem_shares_one_buffer_and_clones_share_every_buffer`, `separated_stems_and_the_original_are_shared_not_copied`, and the type: `Samples` has a private field and derefs only to `&[f32]`.  Clippy's `disallowed-methods` (CI `clippy` job, both targets) fails `slice::to_vec` in `app`, `stem-worker`, `decode-worker`, `stem-protocol`, `engine`, `roformer` and `roformer-gpu`.  It also fails `js_sys::Uint8Array::to_vec` and `js_sys::Float32Array::to_vec` in `app`, `stem-worker`, `decode-worker` and `stem-protocol`.  A needed copy carries an `#[expect]` with its reason.  The page saves a chosen song from the browser's files, not their bytes, and reads no source to open it: `an_open_posts_a_decode_and_reads_no_source` (CI `browser-tests` job).  `a_stored_song_is_shown_with_no_samples` (CI `browser-tests` job) checks that a stored song of 4 minutes opens with no lane in memory and at most 4 MB more heap than one of 1 minute, and that no read is more than a block of a lane.  `a_stored_separation_shows_its_stems_with_no_read` and `rebuild_shows_complete_stems_as_stored_lanes` (CI `browser-tests` job) check that the stems show with no read of their data.  `a_stem_with_no_overview_stays_a_stored_lane` (CI `browser-tests` job) checks that a complete stem whose overview cannot be made is not read whole.  `the_memory_input_comes_from_the_lanes_in_memory` (CI `test` job) checks that the memory path's input shares the original lane's samples.  `the_page_reads_a_lane_one_block_at_a_time` and `a_mix_change_with_spectrograms_on_holds_no_song_sized_buffer` check that the jobs read a block at a time.  The exceptions: `the_memory_path_reads_a_stored_input` and `unstored_refuses_a_long_song`, `an_incomplete_stem_is_read_whole_only_on_the_memory_path` (CI `browser-tests` job), `the_classic_drums_route_follows_where_the_input_lanes_are` and `classic_drums_in_memory_counts_its_mix_and_its_new_lane` (CI `test` job), and `classic_drums_on_the_page_refuses_past_its_limit` (CI `browser-tests` job).  An open that decodes on the page keeps the same limit, and reads only each file's head to refuse a long song: `a_drop_with_no_storage_refuses_a_long_wav_from_its_head`, `a_wav_of_no_stated_length_is_capped_then_stopped_at_the_limit`, `a_file_larger_than_its_stated_length_allows_is_refused_from_its_head`, `a_restore_on_the_page_refuses_a_long_song_from_heads_or_meta` and `a_restore_from_meta_refuses_a_file_larger_than_its_length_allows` (CI `browser-tests` job), and `the_memory_path_shares_seven_lanes_of_its_limit` (CI `test` job).  Then it holds one file's bytes at a time: `a_page_open_holds_one_file_at_a_time` and `a_page_restore_holds_one_file_at_a_time` (CI `browser-tests` job).  `an_mp3_is_encoded_in_blocks` and `a_flac_is_encoded_in_blocks` (CI `browser-tests` job) bound the peak memory of an MP3 and a FLAC encode.  `a_stored_flac_keeps_the_worker_memory_flat` and `a_stored_mp3_holds_at_most_four_times_its_file` (CI `browser-tests` job) do the same for an encode of a save's WAV file.  `a_wav_save_of_a_stored_mix_writes_whole_blocks_through_one_array` (CI `browser-tests` job) checks that a save holds no song-length buffer in WebAssembly memory.  `a_save_that_storage_refuses_is_held_in_memory_only_for_a_short_song` and `a_failed_stored_encode_saves_again_in_memory_only_for_a_short_song` (CI `browser-tests` job) check that only a song within `MEMORY_PATH_MAX_FRAMES` saves through song-length JS arrays.  `a_stored_mix_keeps_the_worker_memory_flat` (CI `browser-tests` job) checks that the worker reads a stored mix one span at a time.  `the_mix_write_makes_no_song_length_buffer` and `write_mix_reads_lane_audio_in_blocks` (CI `browser-tests` job) check that the page writes the mix with no song-length buffer, from lanes in memory or in browser storage.  `a_block_decode_keeps_its_memory_flat` (CI `test` job) and `a_decode_keeps_the_worker_memory_flat` (CI `browser-tests` job) check that the decode worker holds no song-length buffer.  `a_block_hpss_keeps_its_memory_flat` (CI `test` job), `an_overview_request_keeps_the_worker_memory_flat` and `a_classic_request_keeps_the_worker_memory_flat` (CI `browser-tests` job) check the same mapping into WebAssembly memory when it is read as a slice.  The `#[expect]`s in `mem1_lint_is_on` and `mem1_lint_is_on_for_js_arrays`, under the clippy steps with `--all-targets`, prove each path.
* Gaps: TD-26, TD-54, TD-58, TD-59.

### MEM-2: JS arrays are transferred between page and worker

A typed array sent between the page and the worker goes in the message's transfer list, so it moves instead of being cloned, and the receiver does not copy it again without a reason.

* Why: a structured clone of a stem doubles it until garbage collection, which Safari runs late.
* Enforced by: `a_mix_is_transferred_not_copied`, `an_mp3_reply_reaches_the_page_as_sent`, `a_stored_mix_arrives_with_its_path_and_frames` (CI `browser-tests` job).  Since M4, `a_mix_is_transferred_not_copied` covers only the two arrays of the memory path.  On the storage path, no samples cross: `a_stored_mix_arrives_with_its_path_and_frames` checks an empty transfer list.  `a_stored_encode_asks_the_worker_with_paths_only` and `flac_and_mp3_saves_post_paths_then_offer_the_workers_file` (CI `browser-tests` job) check the same for a save's encode.  MEM-1's lint on `js_sys::Uint8Array::to_vec` and `js_sys::Float32Array::to_vec`, where the receiver copies.
* Gaps: TD-26.

### MEM-3: GPU buffers are freed when dropped

Every buffer `roformer-gpu` makes is a `GpuBuffer`, which calls `destroy()` when dropped.  Clippy fails five ways to make a buffer in `roformer-gpu` outside `GpuBuffer`.  No other crate reaches a `Gpu`'s device.  `Rec` borrows the buffers it binds until it is submitted.

* Why: wgpu's web backend does nothing when a buffer is dropped, and Safari's garbage collector does not count WebGPU memory ([WebKit bug 283321](https://bugs.webkit.org/show_bug.cgi?id=283321)).
* Enforced by: `a_dropped_buffer_is_destroyed`, `a_failed_load_frees_what_it_uploaded` (need a GPU, so not in CI; `STEMYLA_REQUIRE=gpu` makes them fail where no adapter opens), and a doctest showing that `Rec` keeps a buffer alive until submitted (it must fail to compile; CI `test` job).  Clippy's `disallowed-methods` in `roformer-gpu` (CI `clippy` job) fails `wgpu::Device::create_buffer`, `wgpu::util::DeviceExt::create_buffer_init` and two wgpu helpers that make buffers, in three paths.  `mem3_lint_is_on` proves each path, under CI's native `--workspace --all-targets` clippy step.  `Gpu`'s device and `Gpu::from_device` are private.  Doctests on `Gpu` fail if either becomes public (CI `test` job).
* Gaps: TD-8, TD-22, TD-27.

### MEM-4: the tab stays under 2 GB on an iPhone

iOS stops a tab whose memory passes 2 GB on an iPhone 17 Pro, however much memory is free, and counts its GPU buffers.  The parameters take about 700 MB on the GPU and one chunk's activations about 280 MB, so everything else stays small.  `docs/ARCHITECTURE.md` (memory on phones) has the design.

* Why: a tab over the limit is killed with no error the page can catch.
* Enforced by: in part.  `xtask e2e old-session` (CI `browser-tests` job) asserts the page's part after the restore of a session of the M4 layout.  The page's WebAssembly memory stays under 64 MB and does not grow with the song.  `xtask e2e memory-budget` (with the model, not in CI) asserts that the page and the workers do not grow with the song during an open and a separation.  `xtask e2e save` asserts that the page's JS heap during a save, and the stem worker's WebAssembly memory during a FLAC encode, do not grow with the song, and bounds an MP3 encode (CI `browser-tests` job, in Chrome).  Nothing asserts the whole tab's peak, GPU buffers included: the worker logs `memory: ...` after every chunk, and M10 of `plans/active/stream-from-storage.md` adds the check.
* Gaps: TD-11, TD-54, TD-58, TD-59.

### MEM-5: browser-storage writes pass a whole array

Every OPFS `write` gets a whole typed array or a Blob, never a view into a larger buffer.

* Why: Safari 27 writes a view's whole underlying buffer (`docs/references/browser-quirks.md`).
* Enforced by: `a_view_is_written_whole`, `sources_are_saved_from_their_files`, `opfs_write_writes_more_than_one_slice`, `a_download_holds_only_the_bytes_of_its_chunks`, `stem_writes_pass_whole_arrays`, `stored_encodes_write_whole_arrays_as_they_read`, `a_wav_save_of_a_stored_mix_writes_whole_blocks_through_one_array`, `stored_stems_replace_the_kept_stems`, `the_mix_is_written_in_whole_blocks`, `write_mix_reads_lane_audio_in_blocks`, `decode_writes_pass_whole_arrays` (CI `browser-tests` job, in Chrome).  Each spies on `write`, so a view fails it in Chrome, not only in Safari.  The spy does not see a new OPFS write that has no spy test of its own.

## Audio

### RT-1: the audio callback never waits, frees a player or allocates after warm-up

The audio callback reads the player through `engine::slot`'s `try_lock`, renders silence when the slot is busy or empty, and never drops a `Player` or `Song`: the old player is handed back to the caller, which frees it on its own thread.  The warm-up is `Player::with_sources` (which `Player::with_config` calls) and `ReadAhead::new`, on the thread that makes the player.  After it, the callback never allocates or frees memory, for the stretchers the app ships.  `Stretcher::warm_up` makes a stretcher's buffers reach their largest size first.

* Why: a callback that blocks or frees a song's buffers misses its deadline and is heard as a click; on the web, cpal's callback is never freed, so anything it holds leaks.  An allocator can take a lock or fault a page, so its time has no bound (`decisions/0007-no-allocation-in-the-audio-callback.md`).
* Enforced by: `replacing_the_player_frees_the_previous_song`; `the_callback_does_not_allocate_after_warm_up`, `a_stretcher_keeps_its_warm_up_promise` and `the_app_ships_only_these_stretchers` (CI `test` job).  The first runs the callback under a counting allocator, through tempo, chipmunk, seek, loop and mix changes, for each stretcher the app ships.  The second checks what `Stretcher::warm_up` promises, at rates from 8 to 192 kHz.  `Player::with_sources` and `Varispeed::warm_up` panic on a configuration that the warm-up cannot cover.  The third fails when `app/Cargo.toml` turns on a stretcher that the first does not cover.  The first also plays the stems as stored lanes over a `ReadAhead`, with the phases "reader stalls", "seek holds", "loop behind the head", "seek held at the end" and "lane fails".  `a_held_slot_never_blocks_the_callback` (CI `test` job) checks that the callback takes a slot of the read-ahead buffer with a try-lock only.  `a_slot_whose_block_changed_is_not_read` checks the block number again under the lock.
* Gaps: TD-25, TD-40.

## GPU

### GPU-1: every kernel fits WebGPU's default limits

Kernels fit the default limits (`docs/references/webgpu-limits.md`), and the device is requested with exactly those (`Limits::defaults()` in `roformer-gpu/src/lib.rs`), so nothing depends on what one GPU offers beyond them.

* Why: a kernel that needs more fails on some users' GPUs only.
* Enforced by: `every_kernel_fits_the_default_limits` (CI `test` job), and wgpu's validation at runtime on a real adapter.  The test parses every shader with naga, generated sources included.  It checks the workgroup size, the invocations and the workgroup storage of each entry point, the storage and uniform buffers, and the bind groups.  `every_layout_matches_its_shaders` checks that the layouts bind what the shaders declare.  Dispatch counts and buffer sizes depend on the data.  `Rec::push` asserts each dispatch count, and only wgpu checks buffer sizes.  `workgroup_memory_within_defaults` also checks the tile sizes against their formula.  `sources_are_complete` makes sure that no generated source has an unfilled placeholder.
* Gaps: TD-41.

### GPU-2: a kernel change is checked against the CPU and in a browser

Every change to a kernel is checked against the CPU (`STEMYLA_REQUIRE=gpu cargo test -p roformer-gpu --release`) and in a browser (`?selftest`, or `cargo run -p xtask -- e2e selftest --weights <model>`, with `--query` naming the kernel) before it becomes a default.

* Why: kernels are hand-written WGSL; the CPU network is the reference.
* Enforced by: `matmul_variants`, `attention_matches_cpu` (need a GPU, so not in CI; `STEMYLA_REQUIRE=gpu` makes them fail where no adapter opens), and the kernel checks that run when a GPU opens (`docs/ARCHITECTURE.md`, running it on the GPU).
* Gaps: TD-8.

### GPU-3: never the default on SwiftShader alone

A new kernel is never made the default on the strength of SwiftShader (or any software adapter) alone; it needs a pass on a real GPU, named in the PR.

* Why: SwiftShader's compiler and timing differ from real GPUs; correctness there says little about speed or about other compilers.
* Enforced by: prose only.
* Gaps: TD-10.

## Messages

### PROTO-1: one encoder and one decoder per message, for both sides

`stem-protocol` has one encoder and one decoder per message, shared by the page and the worker.  `xtask e2e` also writes messages by hand (`xtask/e2e/worker.js`, `xtask/src/e2e.rs`), so the wire format changes only together with it.

* Why: the page and the worker are built together but run as separate wasm modules; a mismatch fails at runtime only.
* Enforced by: `replies_arrive_intact`, `requests_and_their_settings_arrive_intact`, `hand_written_requests_are_read`, `decode_messages_arrive_intact_with_nothing_transferred`, `a_message_for_one_worker_is_not_read_as_one_for_the_other`, `worker_requests_and_the_new_replies_arrive_intact_with_nothing_transferred`, `an_overviews_or_classic_request_with_a_missing_or_wrong_field_is_refused`, `a_stored_encode_names_its_files_and_transfers_nothing`, `an_encode_must_name_one_source_with_whole_frames_and_an_output`, `a_stored_encode_reply_names_its_file_or_why_it_failed` (CI `browser-tests` job), and `e2e_messages_use_protocol_types` (CI `test` job).  The last compares the message types in `xtask/e2e/*.js`, and in the scripts of `xtask/src/e2e.rs` and of each Rust file under `xtask/src/e2e/`, with `stem_protocol::kind` and `stem_protocol::decode::kind`.  It does not read field names.
* Gaps: TD-16, TD-42.

### PROTO-2: a model URL only from the page's own site

`?model_url=` skips the model's hash check, so it is accepted only from the page's own site.

* Why: otherwise a crafted link could make the page run a model of an attacker's choosing.
* Enforced by: `a_model_url_is_taken_only_from_the_pages_own_site` (CI `browser-tests` job).

## Verification and process

### VERIFY-1: every behaviour has an automated check

Every behaviour is verified by an automated check; "it compiles" is not acceptance.  A test that skips (no GPU, no fixture) says so, and a skip is not evidence that the behaviour works.  A test that skips calls `test_support::skip`.  The exceptions are allowlisted in `xtask/src/rules.rs`, because a wasm test cannot read the variable.  They are the wasm tests in `app/tests/web_output.rs` and `app/src/streamtest.rs`, and `a_read_back_is_copied_into_wasm_memory_once` in `worker/src/web/tests.rs`.  The last skips in a browser with no GPU adapter, so it can pass in CI with no assert (TD-8).  Where evidence is claimed, `STEMYLA_REQUIRE` (for example `gpu`, `timestamps`, `fixtures`) turns the skip into a failure.

* Why: the most frequent review finding in this repo's history was a test that could not fail (`docs/harness.md`).
* Enforced by: CI (`.github/workflows/ci.yml`) and review.  `every_skip_can_be_required` fails a skip message that does not go through `test_support::skip`, and `the_skip_allowlist_is_current` fails a stale exception.  `a_required_need_that_cannot_run_fails` and `a_required_skip_fails_and_names_the_caller` check that a required skip fails.  CI's `test` job compares the UI snapshots in `app/tests/ui.rs` with the committed PNGs, and `no_build_file_updates_snapshots` keeps `UPDATE_SNAPSHOTS` out of the build files.
* Gaps: TD-8, TD-19, TD-29, TD-39, TD-40, TD-43, TD-51, TD-53, TD-60.

### GIT-1: push only when asked, never to main or gh-pages; never publish or merge a PR

Never push without being asked.  An agent never pushes to `main` or `gh-pages`, runs `xtask publish` (which pushes) or merges a PR; a person does.

* Why: pushing to `main` or `gh-pages` publishes the site, and merging a PR pushes to `main`.
* Enforced by: deny rules in `.claude/settings.json`, kept by `claude_settings_hold_the_deny_rules` (CI `test` job).  They refuse a push that names `main` or `gh-pages`, `--all`, `--branches`, `--mirror`, publish and merge.  They match the command text that an agent usually writes, and were checked by hand (harness phase 2, M14).  On GitHub, the `main` ruleset refuses a direct push to `main`, admin included (TD-20).  A push that names no branch, and a push unasked, rest on prose (decision 0010); TD-28 lists the gaps.
* Gaps: TD-20, TD-28.

### GIT-2: small, verified, signed commits

Work in small verified steps.  `cargo fmt --all --check`, clippy with `-D warnings`, the tests and `xtask docs-check` pass before every commit, and every commit is signed (`git commit -S`).

* Why: a commit is the unit that review, bisect and revert work with; a signature attributes it.
* Enforced by: CI's required checks on `main` (fmt, clippy, test, wasm build, browser tests), which an admin can bypass (TD-20).  A PostToolUse hook in `.claude/settings.json` runs rustfmt on each `.rs` file in the repo that the agent's `Edit` or `Write` tool changes, kept by `the_rustfmt_hook_formats_rust_files`.  It saves a round trip; the `fmt` job is the control.
* Gaps: TD-20.

### GIT-3: gh-pages is never squashed or rewritten

Publishing a build id again keeps its published copy, so `gh-pages` needs its full history: never squash or rewrite it, and publish from a full clone.

* Why: `README.md` (publishing on GitHub Pages) explains the write-once `v/<id>/` folders.
* Enforced by: the `gh-pages history` ruleset on GitHub (id 25544673), which blocks force pushes and deletion of `gh-pages` for everyone, admins included (checked 2026-10-21 with `gh api repos/lloydmeta/stemyla/rules/branches/gh-pages`).  Nothing in the repo checks that the ruleset stays.
