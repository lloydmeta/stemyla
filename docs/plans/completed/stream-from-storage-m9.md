# Stream from storage, M9: f16 weights on the GPU

## Purpose

This is the milestone plan for M9 of `plans/completed/stream-from-storage.md` (the parent plan).  It gives more detail than the parent's M9 section, which stays the criteria.  After M9:

* The GPU keeps each weight matrix of an f16 model file as f16, two values in each `u32` (decision 0018).  The kernels unpack each value to f32 and compute in f32, so each kernel gets the same f32 values as today.
* The parameters on the GPU fall from about 699 MB to about 350 MB.  M10's budget counts on this saving.
* f16 weights become the default only when this Mac's GPU (AMD Radeon Pro 5500M) gives the same stems bit for bit as f32 weights, and `?bench` shows no slower separation (the maintainer's rule, decided in advance).  `e2e weights` also times a whole separation of each format (D11), which is stricter than the rule.  Else the f16 path stays behind `?weights=f16`, and the team leader stops and reports.

Since review round 1 (2026-10-30), part 3 of `e2e weights` is a measure only, and D12 passed on the maintainer's rule (Decision log).  The user sees no change in the stems.  On a phone, the tab has about 350 MB more room.

Facts from outside the repo, checked on 2026-10-29:

* WGSL `unpack2x16float(e: u32) -> vec2<f32>`: component `i` is the f32 value of bits `16 i` to `16 i + 15` of `e` as an IEEE-754 binary16 value ([WGSL, 17.10.7](https://www.w3.org/TR/WGSL/#unpack2x16float-builtin)).  So element `2 j` of a little-endian f16 array is component 0 of `u32` `j`.  Every f16 value, subnormals included, is an exact normal f32 value.
* WGSL lets an implementation flush to zero "intermediate result values of operations listed in ... § 17.10 Data Unpacking Built-in Functions" ([WGSL, 15.7.2 Differences from IEEE-754](https://www.w3.org/TR/WGSL/#differences-from-ieee754)).  So a GPU can turn an f16 subnormal weight into 0.  WGSL also lets a GPU flush the inputs and outputs of the operations of 15.7.4 (arithmetic among them), and ignore the sign of a zero.  These do not concern the f16 path, since every f16 subnormal is a normal f32, and the f32 path has the same arithmetic.
* The real model file (`bs_roformer_sw.f16.safetensors`) has 174,162,944 values in weight matrices and 493,556 in vectors, all F16.  1,043,179 matrix values (0.6%) and 1,341 vector values are f16 subnormals.  No tensor has an odd number of values.  (Counted by the team leader with a Python script in the scratchpad that reads the safetensors header and counts the values whose exponent bits are 0 and mantissa bits are not.)  So a GPU that flushes changes the stems.
* naga 30.0.1 accepts `unpack2x16float` only with `Capabilities::SHADER_FLOAT16_IN_FLOAT32` (`src/valid/expression.rs`).  wgpu 30.0.1 grants it from `DownlevelFlags::SHADER_F16_IN_F32` (`wgpu-naga-bridge` 30.0.1, `src/lib.rs`; decision 0018).  wgpu-hal's Metal adapter starts from `DownlevelCapabilities::default()`, which has the flag, and does not clear it.  wgpu 30.0.1's web backend reports `DownlevelCapabilities::default()` ("WebGPU is assumed to be fully compliant", `src/backend/webgpu.rs`), which has every flag, and gives the WGSL to the browser.

Terms, besides the parent's:

* Weight format: how the GPU holds a weight matrix: `F32` (today) or `F16` (two values in each `u32`).
* f16 variant: the matmul kernel of a tile that reads B as packed f16 and unpacks each value to f32.  The f32 kernel of the tile reads B as f32.

### Decisions of this milestone

* D1, the weight format of a buffer.  A weight matrix on the GPU is a `Weight`: a `GpuBuffer` and its `WeightFormat`, with private fields and no `Deref`, so its buffer cannot pass as an activation.  `Gpu::upload_f16` gives a `Weight` (D2), and an f32 weight upload gives one too.  `MatMul`'s B is a typed operand: an activation (`F32`) or a `Weight`, from which `MatMul` reads the format.  So no code path can bind f16 bits to an f32 kernel.  `Rec::matmul` picks the f16 variant of the chosen tile for an `F16` B.  `Kernel::MatMul` and `Kernels::matmul` get one entry for each tile and format.  A profile label of an f16 variant names the format (for example `matmul 1151x1536x256 x1 i64 f16`); f32 labels stay as they are.
* D2, the upload.  `Gpu::upload_f16(label, bits: &[u16]) -> Weight` packs element `2 j` in the low 16 bits of `u32` `j` (the little-endian bytes of the file as they are).  An odd count gets one zero value of padding.  The size rounds up to 16 bytes, as `Gpu::buffer` does, so `MatMul::vec4_ok` holds.  It is counted in `created_bytes` and `live_bytes`, and made through `GpuBuffer`'s constructors (MEM-3).  `roformer::weights::Store` gets `dtype(name)` and a read of the raw f16 values of an F16 tensor, which marks the tensor as read, as `get` does.  So `Net` picks the read of each stack before it reads a tensor, and reads none twice.  Only weight matrices are read this way.  Norms, biases and `gamma` stay f32, since the upload scales norms, and the parameters they take are under 2 MB.  An F32 or BF16 tensor, and a stack whose tensors are not all F16, upload as f32 (decision 0018: BF16 can overflow f16).
* D3, the f16 variants.  Each tile of `TILES` gets an f16 variant, generated from the same source as its f32 kernel.  It declares B as `array<u32>` (`array<vec2<u32>>` for `v64`) and unpacks each B value with `unpack2x16float` where it reads it: in `b_get` for the generated kernels, and at the load of line 90 for `s64`.  The rest of the kernel, and so the order of the products and sums, is the same.  The f32 sources stay byte for byte as at `320c521`: `every_shader_file_is_checked` still finds `s64`'s f32 source equal to `matmul.wgsl`, and the stems of the f32 path do not change.  A text substitution that makes a variant asserts that each replaced text occurs exactly once.  A new shader file goes into `SHADER_FILES` or `GENERATED_FROM`.  Products of two activations (the attention scores, P·v, fused attention) keep the f32 kernels.
* D4, the GPU-1 checker.  `limit_breaches` validates with a constant `CHECK_CAPABILITIES`: `Capabilities::default()` and `SHADER_FLOAT16_IN_FLOAT32`, with a doc comment that gives the reason (the f16 variants of decision 0018; the device gets it from `DownlevelFlags::SHADER_F16_IN_F32`).  A test shows that a planted shader that calls `unpack2x16float` fails under `Capabilities::default()` and passes under `CHECK_CAPABILITIES`, and that `CHECK_CAPABILITIES` has no other flag beyond the default.  `generated_sources` adds each f16 variant (`i64-f16` and so on), and the `want` list of `every_kernel_fits_the_default_limits` names them.  `every_layout_matches_its_shaders` and the GPU test `compile_each` cover them too.  `kernels_id` hashes the f16 variants too.
* D5, the start-up check.  `Gpu` keeps the adapter's `DownlevelFlags` (`Gpu::open` passes them to `from_device`).  Without `SHADER_F16_IN_F32`, the f16 variants never compile and the weights are f32.  With the flag, `check_kernels` also runs the f16 variant of each tile that passed, on the two cases whose B is a weight (cases 1 and 3), and on a new case 4 that a flush must change.  Case 4's K is a multiple of 4 and its B is K-contiguous, so `v64`'s f16 variant runs itself, not the `i64` fallback.  In cases 1 and 3, B holds f16-exact values, and about one in eight of them is an f16 subnormal; some are `+0` and `-0`.  In case 4, rows of A are one-hot and columns of B hold only f16 subnormals, so each output is one subnormal f16 value as f32, and a flush gives 0.  A sum of values near 1 can hide a flushed subnormal; case 4 cannot.  The f32 kernel of the same tile runs on the same values as f32.  The f32 check against the CPU keeps today's random B; the f16 check adds its own runs with the f16-exact B.  The two outputs must be equal bit for bit (`f32::to_bits`, with `+0` and `-0` counted as equal, since WGSL lets a GPU ignore the sign of a zero).  `Gpu::f16_ok` is true only when every tile that passed its f32 check also passed its f16 check.  Else the weights stay f32, and `check_kernels` gives a line that names the tile, how many values differ and the largest difference.  When it passes, the worker logs `f16 weights: the start-up check passed`, so a browser test and M10's iPhone run can see it.  Why one switch for all tiles: the stems of the f16 path must equal the f32 path with the same kernel choice, and a flush comes from the unpack, which every variant shares.
* D6, the choice of format.  A pure function, `weight_format(setting, flags, f16_ok)`, gives `F16` only when the setting allows it, the adapter has `SHADER_F16_IN_F32` and `f16_ok` is true.  The setting is `Settings::weights` from `?weights=` (`f32`, `f16` or `auto`, D9).  `f32` gives `F32`.  `f16` gives `F16` when the GPU allows it, else `F32` with a log line.  `auto`, or no setting, gives the default, `DEFAULT_WEIGHTS`.  Until step 5, `DEFAULT_WEIGHTS` is `F32`, so steps 1 to 4 change no stems and no memory.  `Net::load_store` takes the format.  `Net` records the format that it uploaded: `F16` only when every weight matrix went up as f16 (an F32 or BF16 file gives `F32` whatever the setting).  The worker's `memory: ...` line, `ensure_kernels` (D7) and D10's checks read the format from `Net`.  The `memory: ...` line names it: `model on the GPU 350 MB (f16 weight matrices)` or `model on the GPU 699 MB (f32 weights)`.  A test without the downlevel flag gets `F32` for every setting.  A GPU test checks that a `Gpu` whose flags lack `SHADER_F16_IN_F32` compiles no f16 variant, sets `f16_ok` to false, and loads a net as `F32` with the `f16` setting.  It is in `roformer-gpu/tests/memory.rs`, beside the synthetic store, and opens its device with a `#[doc(hidden)] pub async fn` of `Gpu` that masks the flag from the adapter's flags.  It is not a unit test, since CI runs `cargo test -p roformer-gpu --lib` on lavapipe and those tests need no GPU (`ci.yml`).  `from_device` stays private (MEM-3; the `compile_fail` doctest of `lib.rs` pins it, with the new signature).
* D7, calibration.  `calibrate` takes the weight format, and times the linear shapes (`Kind::Linear`) with weights in that format; the scores and P·v stay f32.  `choose_kernels` keeps the choice under the key `"{adapter}|{kernels_id}|{CALIBRATION}|{f32 or f16}"`, so the two formats do not share a choice.  `KEEP_PER_GPU` goes from 3 to 6, since each build can keep two keys.  The worker chooses once per format, not once per worker: `kernels_chosen` becomes the format of the last choice, and a load of the other format chooses again.  Before it chooses again, the policy and the attention path go back to their state after the start-up checks, and then the URL's overrides apply.  The worker logs the choice that it uses, with where it came from: `kernels: matmul <policy>, attention <policy> (stored, calibrated or from the URL; f32 or f16 weights)`.  `ensure_kernels` uses the loaded model's format; `?bench` without a model uses the format that a load would take.  `CALIBRATION` goes from 2 to 3.  The key and the test of whether to choose again are pure functions with native tests, and `stored_choices` (`bench.rs`) gets a case with f32 and f16 keys at a keep of 6.
  * So the two formats can get different kernels on one GPU.  That is not a change of the f16 path's arithmetic: each kernel of each format is checked bit for bit against the f32 kernel of the same tile (D5).  The bit-for-bit check of the stems (D10) passes the same kernels to both formats.
* D8, `?bench`.  On a GPU with `f16_ok`, `measure` times each linear shape with each kernel and both formats, the formats taking turns within each round as the kernels do, so a GPU that heats up slows both alike.  Its log lines name the format.  `summary` gives the matmul seconds per chunk for each format (each kernel alone, and the best kernel per shape), and two lines with the ratio of f16 to f32 for the best kernel per shape: over the whole chunk, and over the linear shapes only.  The scores and P·v run the f32 kernels in both formats, so the f16 total takes their f32 timings, and the ratio over the whole chunk is nearer 1.  On a GPU without `f16_ok`, `?bench` times f32 only and says why.
* D9, the switch on the wire (PROTO-1).  `Settings` gets `weights: Option<String>`, read from `?weights=` and sent with each request, as `mm` is.  The `stem-protocol` round-trip tests cover it.  The new scenario (D10) sends it by hand.  `stored-stems` sends no `weights`: it takes the default, and its hashes hold for either format when D10 passes.  README's list of page parameters names it.
* D10, the evidence of the decision point: a new scenario, `xtask e2e weights`, with the real model (`--weights`), from blank pages, driven by hand as `stored-stems` is.  Each `e2e.ask` call starts a new worker and posts all its messages before any reply (`xtask/e2e/worker.js`).  So a load that needs a reply of an earlier one is a new call:
  * Part 1, the pinned kernels.  It loads the model with `weights: 'f32'` and its bytes, separates the 3-second clip of `stored-stems`, then loads it from browser storage with `init` and `weights: 'f16'`, and separates the same clip.  So the page posts the model once.  Both use `chunk: 16384, overlap: 2, mm: 's64', attn: 'split', step_limit: 600` (the settings of M3's hashes).
  * Part 2, this GPU's own kernels at the default chunk.  It loads the model with `weights: 'f32'` and `mm` and `attn` unset, so the worker calibrates or takes its stored f32 choice.  It reads the worker's `kernels: ...` line (D7) and separates the clip.  Then, in a second call, it loads the model with `weights: 'f16'` and the f32 choice as `mm` and `attn`, and separates the clip.  So both formats run the same kernels.
  * For each separation it prints the SHA-256 of each stem's f32 samples, the SHA-256 of each stem as a 16-bit WAV (as `stored-stems` prints), and the worker's `memory: ...` lines.
  * It checks that the f32 and f16 stems are equal bit for bit, in both parts.  If not, it prints, for each stem, how many values differ, how many of them differ only in the sign of a zero, and the largest difference.  It checks that part 1's f32 16-bit hashes equal M3's six hashes (`stream-from-storage-m3.md`, Progress), so the f32 path is unchanged.  It checks that the worker's log names the format of each load, that the f16 load's parameters are under 360 MB, and that the f32 load's are over 690 MB.
  * Its pure checks are functions with native tests, as `e2e save`'s are.  The scenario does not run in CI, since CI has no real model.
* D11, "no slower separation".  Since the Decision log entry of review round 1 (2026-10-30), part 3 below is a measure only.  On this Mac in Chrome, f16 is not slower when both hold:
  * the full `?bench` (not `bench_quick`) gives f16's matmul seconds per chunk over the linear shapes only, best kernel per shape, at most the bar above f32's in the same run.  The whole-chunk line is not the gate: the scores and P·v take about a third of a chunk's work and share their f32 timings, so they would hide part of a slowdown;
  * part 3 of `e2e weights`: each format with its own kernel choice (`mm` and `attn` unset, D7), at the default chunk, on a clip of at least 4 chunks (the synthetic song repeated, about 60 s).  Part 3 is one `e2e.ask` call, so one worker and one device.  One warm-up separation of each format comes first, and is not counted, so the GPU's clocks and caches settle (the start-up checks have compiled the pipelines already).  The time of a separation is the `secs` of its `done` reply.  Then the formats take turns in the order f32, f16, f16, f32, f16, f32, f32, f16, so a GPU that heats up does not favour one format.  The measure is the median of four times for each format.  The model goes into browser storage once, with the first `model` message and its bytes.  Each later load is an `init` message with the format's `weights`, which builds the net from the stored copy (`worker/src/web.rs`, `init`), so the page does not post 350 MB again.  A load comes before each separation, outside the timed part.  f16's median must be at most the bar above f32's.  The first load of each format logs a `kernels: ...` line that names that format; the scenario checks it, so f16 does not run on f32's choice.
  * The bar is 2%, or the spread of the f32 measures if it is larger, up to 5% (superseded for part 3: Decision log, review round 1).  If a spread is over 5%, the measure runs once more.  If it is still over 5%, the team leader records the numbers, and stops and reports (D12).  In the bench: |f32 linear total of run 1 - f32 linear total of run 2| / their mean, and f16 must pass in both runs.  In part 3: (largest - smallest) / median of the four f32 times.  Progress records each number and the bar used.
  * Part 3 is stricter than the maintainer's rule, which names `?bench`: the bench times only the matmuls, and a separation also unpacks in the staging loops that the bench shares, plus everything else of a chunk.  A slower separation would break the rule's intent.
* D12, the default.  If D10's stems are equal bit for bit and D11 holds, step 5 sets `DEFAULT_WEIGHTS` to `F16`.  The team leader's report then asks the maintainer to accept decision 0022, whose fallback the default relies on.  Else `DEFAULT_WEIGHTS` stays `F32`, the f16 path stays behind `?weights=f16` with its tests, the numbers go into Progress, and the team leader stops and reports to the orchestrator.  If the Mac flushes f16 subnormals (D5's check fails), the team leader reports that too, with the counts.  One option for the orchestrator then is an exact unpack in integer arithmetic (an f16 subnormal is `m x 2^-24`, which is an exact normal f32), which WGSL does not let a GPU flush; it changes decision 0018's means, so it is the maintainer's choice.  Safari: if Safari rejects an f16 variant (step 3), D12 does not pass, since the iPhone runs Safari; the team leader stops and reports.  A failed f16 start-up check in Safari (a mismatch, not only a compile error) stops D12 too.  If the Safari session cannot start or times out (a driver problem, not a shader result), the team leader records it with a `docs/tech-debt.md` entry, reports it, and goes on: on such a Safari, D5's start-up check keeps the weights f32.
