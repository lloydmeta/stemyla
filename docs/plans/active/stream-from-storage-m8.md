# Stream from storage, M8: saving reads from storage and writes to storage

## Purpose

This is the milestone plan for M8 of `plans/active/stream-from-storage.md` (the parent plan).  It gives more detail than the parent's M8 section, which stays the criteria.  After M8:

* A save of a stem or of the mix as heard writes its file to browser storage (OPFS) in blocks, and the page offers that file as the download.  No save makes a song-length array in the JS heap or in WebAssembly memory, except the memory path's bounded JS sinks (D8) and the MP3 encoder's frames in the stem worker (the MP3 exception of D4).
* A WAV save is the page's file.  For a FLAC or MP3 save, the stem worker reads the page's WAV file in blocks, encodes it, and writes the encoded file to browser storage in blocks.  The page offers the encoded file as the download.
* When browser storage is unavailable, or a save's write fails, a song of at most `MEMORY_PATH_MAX_FRAMES` frames saves as today, through the JS sinks (decision 0015, the memory path as the fallback).  A longer song does not save, and the status line says why.

The user sees the same Save menu, the same file names and the same files: a WAV and a FLAC are bit for bit as before.  An MP3 is encoded from the 16-bit samples of the WAV, not from the 32-bit mix (D2).

## Context and orientation

The state at the start of M8, on 2026-10-28, at commit `c3952ad` on the branch `iphone-crashes-2026-10-25`.  The parent plan's "The code today" and "Terms", and the plans of M3 to M7 and of the catch-up (`stream-from-storage-m3.md` to `-m7.md`, `stream-from-storage-catchup.md`), apply.  These parts concern M8:

* `app/src/export.rs`: `ExportJob<S: Sink>` reads a `Pcm` source in blocks of `BLOCK` (16,384) frames and writes each block to its `Sink` (`write(&mut self, at, left, right)`).  `run_while(more)` steps while `more` says there is time; it returns at once while the source is not ready (`is_waiting`).  `stopping_at_a_failure` ends the job at the first failed read of storage.  The web sinks: `JsWav` (a whole WAV in one `Uint8Array`), `JsChannels` (two song-length `Float32Array`s), and `JsSink`, which picks one of them for a format.  `JsChannels` is also the memory path's input (`MemoryInput` and `read_memory_input` in `app/src/lib.rs`, bounded by the memory path's limit); M8 keeps that use.
* `app/src/lib.rs`: `save_menu`, `start_save` and `step_save`.  `start_save` makes the source (`lanes::LanePcm` for a stem, `lanes::LanesMix` for the mix as heard) and a `JsSink`.  `step_save` runs the job for `SAVE_MS` (4 ms) in each UI frame.  At the end, a WAV goes to `store::download`, and FLAC and MP3 go to `Separator::encode_flac` and `encode_mp3` with the two arrays, transferred (MEM-2).  The worker's file comes back as `Event::Flac { name, file: Blob }` or `Event::Mp3 { name, bytes }`, and the page calls `store::download_blob` or `store::download`.  `SaveNotes` keeps the "it clips" note of each file until its reply.  `save_menu` disables Save while `saving` is `Some`, that is while the page's job runs, not while the worker encodes.
* `app/src/store.rs`: the JS glue (`st_open`, `st_put`, `st_close`, `st_abort`, `st_remove`, `st_file`, `save_blob`).  `save_blob` makes an object URL, clicks a link with `download`, and revokes the URL after 60 s.  `write_mix` and `put_mix_blocks` write `mix.f32` in blocks of `MIX_BLOCK_FRAMES` (131,072 frames, 1 MiB) through a `FileSystemWritableFileStream`, each block a new whole array (MEM-5).  `start_spy` and `stop_spy` are the page's MEM-5 spy on `write`.
* `worker/src/web.rs`: `mp3` and `flac` take two `Float32Array`s and read them in blocks (`MP3_BLOCK`, `FLAC_BLOCK`).  `mp3` collects the whole MP3 in a `Vec<u8>` in WebAssembly memory, then sends it as one `Uint8Array`.  `rusty_mp3` 1.0.0 keeps every encoded frame until `finish()` too, because it turns on its bit reservoir for CBR at 256 kbps or less on MPEG-1 (`push_with` and `finish` in its `src/lib.rs`; only the `MP3_RESERVOIR` environment variable, which wasm does not have, turns it off).  At these MPEG-1 rates (32, 44.1 and 48 kHz), `next_packet` gives nothing before `finish()`.  At 24 kHz or less the reservoir is off, `next_packet` gives packets during the pushes, and `finish()` puts the Info frame at the front of its queue.  `flac` keeps every encoded frame as a `Uint8Array` in a JS array, then makes one `Blob`.  So the worker holds the whole encoded file.  The encodes do not wait for the worker's turn (`handle`): they run beside a separation.  `pcm16` rounds as `engine::wav::write_pcm16` does: `(x * 32768).round()`, clamped to -32768..32767.
* `worker/src/web/mix.rs`: `StoredMix` reads a file with `FileReaderSync` (`blob_range`) one span at a time.  `worker/src/web/stems.rs`: `StemWriter` writes through `FileSystemSyncAccessHandle`s, each write a whole new `Uint8Array` (MEM-5), and writes the WAV header at offset 0 at the end.  `worker/src/web/tests.rs` has the worker's MEM-5 spy (`stem_writes_pass_whole_arrays`) and a counting allocator (`LIVE`, `PEAK`), used by `an_mp3_is_encoded_in_blocks` and `a_flac_is_encoded_in_blocks`.
* `protocol/src/lib.rs`: `Request::Mp3` and `Request::Flac` (`name`, `left`, `right`, `rate`), `Reply::Mp3 { name, bytes }` and `Reply::Flac { name, file }`.  `Mix` (`Arrays` or `Stored { path, frames }`) is the model for a source that is in storage.  `protocol/tests/web.rs` has the round trips.
* `xtask/src/e2e.rs`: `e2e flac` posts `{type: "flac", name, left, right, rate}` by hand from a blank page and checks the reply's `Blob`.  `xtask/e2e/worker.js` is the e2e helper that starts the worker.  `xtask/src/e2e/old_session.rs` plants a stored session of M4's layout and restores it; its `PLANT` script makes 16-bit WAVs in the page.
* `app/src/reset.rs`: `wipe_opfs` removes every entry at the OPFS root, so it also removes the new `saves` folder.
* Tests of a save today: `a_lane_added_during_a_save_keeps_the_save` and `a_save_whose_read_fails_says_so_and_makes_no_file` (`app/src/playback_tests.rs`), the job and sink tests of `app/src/export.rs`, `a_mix_export_does_not_grow_wasm_memory`, and `an_mp3_reply_reaches_the_page_as_sent` and `a_flac_reply_reaches_the_page_as_sent` (`app/src/separator.rs`).  TD-53 lists the save paths that have no test.
* TD-54 says: "A save keeps its whole file in the JS heap until M8."  MEM-1's "Enforced by" names the encode tests.  `docs/ARCHITECTURE.md` (saving a stem or the mix) draws the JS sinks.

Facts from outside the repo, checked on 2026-10-28:

* Chrome's `performance.memory.usedJSHeapSize` is V8's used heap plus its external memory, which holds the backing stores of `ArrayBuffer`s.  Without the `PreciseMemoryInfo` feature, Chrome rounds the value to a bucket and updates it at most once in 20 minutes.  With `--enable-precise-memory-info`, it reads the value at each call ([Chromium `memory_info.cc`](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/timing/memory_info.cc); the change that added the external memory, 2019: [commit 6a0a099](https://chromium.googlesource.com/chromium/src/+/6a0a09909f0f5bec51931c659da6acbf19dd2b17%5E%21/)).  The page's value does not include a worker, which has its own heap.  MDN marks the API non-standard and deprecated ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Performance/memory)).
* `performance.measureUserAgentSpecificMemory()` needs a cross-origin isolated page (COOP and COEP headers).  It measures at the next garbage collection, after up to 20 s, unless Chrome runs with `--enable-blink-features=ForceEagerMeasureMemory` ([web.dev](https://web.dev/articles/monitor-total-page-memory-usage), [cross-origin isolation guide](https://web.dev/cross-origin-isolation-guide/)).  No source found says that it counts `ArrayBuffer` backing stores.
* `FileSystemWritableFileStream.write` takes the data when it is called; the array can be used again after the promise resolves.  A `File` from `getFile()` is a snapshot: in Chrome, a read after the file changed or was removed fails with `NotReadableError` (M6 plan, facts).

Terms, besides the parent's and those of M3 to M7:

* Save file: a file that a save writes in the `saves` folder at the OPFS root.  The WAV file of a save is the page's; the encoded file of a FLAC or MP3 save is the worker's.
* Offered: a save file for which the page clicked a download link.
* Storage path of a save, and memory path of a save: a save that writes save files, and a save that writes the JS sinks of today.

### Decisions of this milestone

* D1, one WAV file for every save.  On the storage path, the page's `ExportJob` writes every save, of any format, as a 16-bit WAV save file, `saves/<page>-<n>.wav`.  `<page>` is a number fixed when the page starts (its start time in milliseconds), and `<n>` counts the page's saves.  The WAV's header is written first, since the job knows its frames.  For a WAV save, that file is the download.  For FLAC or MP3, it is the worker's input, and the worker writes `saves/<page>-<n>.flac` or `.mp3`.  So the page has one write path, and the worker reads one format.
  * Why not an f32 file for FLAC and MP3: it takes twice the storage (635 MB for 30 minutes, against 318 MB) and twice the writes on a phone.  FLAC is 16-bit, and the WAV's rounding is the worker's `pcm16`, so a FLAC is bit for bit as before.
  * Why not the stem's own session file for a stem save: a stem lane can be in memory (the memory path, the demo song) or an f32 source lane, and a new separation can replace `stems/<stem>.wav` while a download reads it.  One path is simpler to test.
  * The parent says that the worker encodes "from a session file".  The WAV save file is a file in browser storage of the session's audio, but it is not one of the session's files: it is the save's.  This changes the parent's words, not its intent: no song-length array crosses to the worker.
* D2, an MP3 from 16 bits.  The worker encodes an MP3 from the WAV's 16-bit samples, not from the 32-bit mix.  The MP3 of a mix in which no sample exceeds full scale differs from today's by the 16-bit rounding (about -96 dB), far under the noise of a 192 kbps MP3.  A test shows that the stored path's MP3 is the same, bit for bit, as the arrays path's MP3 of the same 16-bit samples.
* D3, the page writes in whole reused blocks within the frame budget.  A new sink, `StoredWav` (web, `app/src/export.rs`), puts the 16-bit bytes of each job block in a WebAssembly buffer of `SAVE_WRITE_BYTES` (1 MiB).  When the buffer is full, it copies it into one JS `Uint8Array` of exactly 1 MiB, made once for the save, and writes that whole array (MEM-5).  The last block gets a new whole array of its own length.  At most one write is in flight.  While a write is in flight, the job waits as it waits for a source that is not ready: it takes no time in the frame, and the write's end asks for a repaint.  So the job keeps `SAVE_MS` (4 ms a UI frame) or less of the main thread, and the JS heap holds one block, whatever the song's length.
  * `Sink` gains `ready(&self) -> bool` (default true) and `failed(&self) -> Option<String>` (default `None`).  `ExportJob` waits while the sink is not ready, and a job that stops at a failure stops at a failed write too.  The pure part (the block buffer, its order and its sizes) is native code with native tests; only the copy into JS and the write are wasm32-only.
  * A done job is not a complete file.  `is_done` depends on the source only, and the last short block, the write in flight and `close()` come after it.  Chrome puts a `FileSystemWritableFileStream`'s writes in the file only at `close()`.  So the sink has an end stage: after the job is done, `step_save` asks the sink to finish (write the last block, then close), and waits for it.  The page offers the file, or posts the encode request, only after the close resolved.  A test checks that the offered `File` has exactly 44 + 4 x frames bytes.
  * A save that the page drops (a new song, `load_song` setting `saving` to `None`, or Reset) aborts its stream and removes its file.  `prepare_reset` sets `saving` to `None` too.  A save counts in `store`'s `WRITES` from `st_open` until its close or abort resolves, as `write_mix` does, so Reset's `store::close` waits for it.  A save that finds `CLOSED` set aborts, removes its file, and does not fall back to the memory path (D8).  Tests: a save dropped during its write leaves no file and no open stream; Reset during a save leaves an empty root and makes no memory-path save.
* D4, the worker reads and writes in blocks.  A FLAC or MP3 request of the storage path names the WAV save file and its frames, and the output file.  The worker opens the WAV with `getFile()`, checks its size (44 + 4 x frames bytes) and reads the data in blocks with `FileReaderSync`, as `StoredMix` reads the mix.  It converts each 16-bit sample to `f32` as `s / 32768` (exact), so `pcm16` gives the same 16 bits back.  It writes the encoded file through one `FileSystemSyncAccessHandle`, a whole new `Uint8Array` for each write (MEM-5), as `StemWriter` does.  FLAC writes its 42-byte stream header at offset 0 first with the frame count still unknown, then again at the end; the test checks that the header has the same length both times.  The FLAC encode holds no list of encoded parts.  At the end of a stored encode, on success or failure, the worker removes its input WAV itself, so the page never has to match an `error` to its WAV.  It flushes and closes the handle before its reply, on success and on failure.  On a failure, it also removes the output file.  It replies with the save's output path and the reason (`Encoded::Failed`, D5), not with `error`, so the page knows which save failed and can fall back (D8).  A malformed request still gives `error`, as today.
  * The MP3 exception.  `rusty_mp3` keeps every encoded frame until `finish()`, and then puts them together (Context).  So an MP3 encode holds the MP3's frames in the worker's WebAssembly memory.  The MP3 is about 1.44 MB a minute at 192 kbps (about 43 MB for 30 minutes).  While `finish()` runs, the banked frames, the whole main-data stream and every output frame are live together: plan review 2 measured a peak of about 3.4 times the MP3's size natively (30 s: a 0.72 MB MP3 and a 2.50 MB peak; 120 s: 2.88 MB and 9.74 MB).  So a 30-minute MP3 save takes about 150 MB of the stem worker's WebAssembly memory, which never shrinks.  Today's `mp3` peaks at about the same; M8 does not make it larger.  The worker writes the MP3's packets to the output file after `finish()`, as `next_packet` gives them, with no copy of its own.  It never writes packets during the pushes, so the Info frame is first at every rate.  The bit reservoir stays on: turning it off needs 320 kbps, which changes the files, or a change to the crate, which is the maintainer's choice.  So M8 adds a `docs/tech-debt.md` entry: an MP3 save holds about 3.4 times its encoded file in the worker, with the bytes per minute measured in step 1, the 30-minute figure, and the options (a reservoir switch upstream, or another encoder).  MEM-1 and MEM-4 name it in their "Gaps".  The team leader tells the orchestrator that M10's budget does not count it yet.  The MP3 bound is in D10 and in step 1's test.  The JS heap of the parent's acceptance does not hold it.
* D5, the wire format (PROTO-1).  `stem-protocol` gets an encode source like `Mix`:
  * `Request::Mp3` and `Request::Flac` take `source: Encode`, where `Encode::Arrays { left, right }` is today's two transferred arrays and `Encode::Stored { wav, frames, out }` names the WAV save file, its frames and the output file, from the OPFS root.  On the wire, the storage path is `{type: "flac", name, wav, frames, out, rate}`, with nothing transferred.  A request with both arrays and `wav`, or neither, or with bad `frames`, or a stored request with no `out`, is refused, as `separate` refuses (a missing field must not decode as a default, TD-16).  The worker refuses a `wav` or `out` that is not in `saves/`, so a page bug cannot remove a session file.
  * `Reply::Mp3` and `Reply::Flac` take `file: Encoded`, where `Encoded::Bytes` (MP3) or `Encoded::Blob` (FLAC) is today's reply, `Encoded::Stored { path }` names the output file, and `Encoded::Failed { path, text }` names the output file of a stored encode that failed, with the reason.  On the wire: `{type: "flac", name, path}` and `{type: "flac", name, path, failed: text}`.  The output path is unique to a save (D1), so the page finds its save by it, not by the name.
  * `xtask e2e flac` and `xtask/e2e/worker.js` change in the same commit.  `e2e flac` keeps its arrays case and adds a stored case: it writes a 5-minute 16-bit WAV to OPFS in the page and checks the stored reply's file.
* D6, the download.  The download of an OPFS `File` through an object URL is new for Safari and the iPhone; only Chrome checks it here.  The team leader asks the orchestrator to add a save of each format to M10's iPhone run.  The page offers a save file with `store::download_file`: it takes the file's `File` with `getFile()` (no bytes are read) and gives `save_blob` a `Blob` of that `File` with the format's type (`audio/wav`, `audio/flac` or `audio/mpeg`), as today's files have.  `new Blob([file], {type})` refers to the file and copies no bytes; an OPFS `File` may have an empty type.  So no bytes of the file enter the JS heap or WebAssembly memory.
* D7, the lifetime of save files.  The page removes:
  * a FLAC or MP3 save's WAV file: the worker removes it at the end of the encode (D4), not the page;
  * an offered save file 10 minutes after the page offered it.  A download reads the file after the click, and the page cannot know when it ends.  Today's object URL lives 60 s, so a download starts within 60 s; 10 minutes leaves time for a long file to be read;
  * at the start of the page, each file in `saves` whose `lastModified` is more than one hour old.  A save of another tab of this site is younger.  So a reload, or a page that stopped before its timer, leaves no file for longer than an hour after the next start;
  * a save file whose write failed, and the file of a dropped save (D3), at once.

  Reset removes the whole OPFS root, `saves` included (`wipe_opfs`).
* D8, the fallback.  The storage path of a save needs a WAV save file that opens and writes.  If the open of the WAV save file fails (`st_open` gives an error: no OPFS, or a refused open), or a write of it fails (for example `QuotaExceededError`):
  * a song of at most `MEMORY_PATH_MAX_FRAMES` frames (100 s) saves through today's JS sinks and array messages.  A failed write first removes its file, then the job starts again on the memory path.  The status line says that the save is held in memory because browser storage failed.  The job is made again from the save's own source: `Saving` keeps the stem index or the save's `MixRecipe`, not the mix as heard at the time of the failure;
  * a longer song does not save.  The status line says that browser storage could not hold the file, and that the user can free space in the Storage menu.  The page holds no song-length array for it.
  * Why the flat `MEMORY_PATH_MAX_FRAMES` and not `memory_path_frames` of the lanes held (decision 0020): the JS sinks are in the JS heap, not in WebAssembly memory, and today every song on the memory path saves through them.  A song held on the memory path is already within `memory_path_frames` of its lanes.  With the lane-shared limit, a 100 s song separated on the memory path (7 lanes, then 8 with the save) could not save when storage is unavailable, which it can today.  The cap only keeps a long stored song, whose storage is full, from making song-length JS arrays.

  A failed stored encode (`Encoded::Failed`, for example no room for the output beside the WAV) follows the same two cases: within the limit, the page saves again on the memory path from the save's source, as above; for a longer song, it says that browser storage could not hold the file.  The page keeps each posted save's output path, the serial of its song and its `lanes_generation`, and its stem index or `MixRecipe` until its reply, for this.  It saves again only when the shown song is still that song with the same lanes (the song's serial and `lanes_generation` both match) and no other save runs (`saving` is `None`); else it waits for the running save to end, and after a new song or Reset it only reports the failure.  A new song or Reset drops the kept sources of posted saves.
* D9, the JS heap measure (the browser test of the parent's acceptance).  `xtask e2e save` measures the page's JS heap with `performance.memory.usedJSHeapSize` in Chrome, run with `--enable-precise-memory-info` and `--js-flags=--expose-gc`.  During each save, an injected script calls `gc()` and reads the value every 250 ms, and once more when the save ends.  The measure is the largest value above the value before the save.  Why this measure:
  * It counts the backing stores of `ArrayBuffer`s (the Chromium source above), which are what today's sinks make.  `measureUserAgentSpecificMemory` has no such statement, needs cross-origin isolation, and resolves only at a garbage collection.
  * The `gc()` before each reading takes out garbage: the read blocks of the lanes are garbage after each block, and their total grows with the song until V8 collects them.  A song-length array is live for the whole save (today's WAV array, `JsChannels`) and stays in each reading, also the last one, before the download.  So the measure sees each song-length array that a save holds, and no garbage.  That is not a weaker check than "no growth of the JS heap with the length": garbage is freed by V8 at thresholds that do not grow with the song, and live memory is what a phone must hold.
  * A calibration check comes first: the scenario allocates a 64 MiB `Uint8Array` in the page and fails unless the measure rises by at least 60 MiB.  So a Chrome that stops counting array buffers fails the scenario; it cannot pass with no check.
  * The worker's part: for each encode, the worker logs a `memory: encode ...` line with its WebAssembly memory in bytes (`memory.buffer.byteLength`) before and after the encode.  WebAssembly memory never shrinks, so the difference includes the encode's peak, within one worker.  The worker's JS heap is checked by the worker tests, not by a reading after the encode: a reading after `gc()` at the end cannot see a peak during the encode, and today's `flac` drops its parts before then.  The checks are that each write is one whole array of at most one block, and that the read and write sequence of step 1 shows a FLAC encode writing each frame before it reads the next block.  When Chrome gives `performance.memory` in a dedicated worker, the line also has the JS heap after `gc()`, as information only.
* D10, the bounds of `e2e save`.  For each format, the 10-minute save's JS heap measure is at most 4 MB above the 1-minute save's (as M10's growth tolerance).  Each reload starts a new stem worker, so the worker bounds use each encode's own growth, from its `memory: encode` line (after less before):
  * FLAC: the 10-minute encode's growth is at most 1 MiB above the 1-minute encode's growth.
  * MP3: each encode's growth is at most 4 times its MP3's size plus 1 MiB, as step 1 bounds the peak (the MP3 exception of D4).  The free heap of a new worker takes part of a small peak, so the 1-minute encode's factor reads low and is not a bound.  The scenario prints each encode's growth divided by its MP3's size, and the tech-debt entry uses the 10-minute figure.  If a correct build needs more, the implementer records the numbers and the reason in the Decision log, and the bound stays under 6 times.

  The order is: WAV 1 and 10 minutes, FLAC 1 and 10 minutes, then MP3 1 and 10 minutes.  WAV saves do not use the worker.  The scenario switches sessions as `old_session` does: it writes `sessions/current` and reloads, and each reload starts a new page and new workers.

  The build of `c3952ad` must fail the page check by far: its WAV sink grows by about 95 MB from 1 to 10 minutes, and its `JsChannels` by about 190 MB.  If a measured run of the new code needs a wider page bound, the implementer records the numbers and the reason in the Decision log, and keeps the bound at least ten times under the base build's growth.  A wider FLAC bound needs the measured numbers and a reason in the Decision log.  The base build keeps its FLAC parts in the JS heap, not in WebAssembly memory, so the FLAC bound is not what fails it; step 1's sequence spy is.  The MP3 bound has no base-build check, since the base build holds the same; its own rule is above.

### Step 1: the wire format and the worker's stored encode (protocol, worker, e2e)

* `protocol/src/lib.rs`: `Encode`, `Encoded`, the new fields and their refusals (D5).  `app/src/separator.rs` changes with it: `encode_mp3` and `encode_flac` take an `Encode`, the reply mapping gives `Event::Mp3` and `Event::Flac` with an `Encoded`, and their tests follow.  The page still posts `Encode::Arrays` in this step.  Update the module doc.  `protocol/tests/web.rs`: round trips of both sources and both replies, an empty transfer list for the stored ones, and the refusals.  `hand_written_requests_are_read` gets a stored request.
* `worker/src/web.rs` (or a new `worker/src/web/encode.rs`): `mp3` and `flac` read from an `EncodeInput` (the arrays, or the stored WAV) and write to an `EncodeOutput` (today's reply, or the stored file), so one encoder loop serves both paths.  The stored path follows D4.  After each encode, the worker logs the `memory: encode ...` line (D9).
* Worker tests (`worker/src/web/tests.rs`), each written to fail first:
  * The stored FLAC is the same, bit for bit, as the arrays FLAC of the same 16-bit samples, for a song of `3 x FLAC_BLOCK + 7` frames and of 30 s.  The stored MP3 is the same, bit for bit, as the arrays MP3 of the same 16-bit samples (D2).  The reply names the output path, and its file decodes (FLAC: `verified`).
  * MEM-5: every write to the output's sync access handle is a whole array (the spy of `stem_writes_pass_whole_arrays`), and each read of the WAV is at most one block.
  * MEM-1: the peak of the counting allocator during a stored FLAC encode of 60 s is not above the peak of 10 s by more than 64 KiB (no growth with the length), and the peak of 30 s is under a tenth of one channel's bytes, as `a_flac_is_encoded_in_blocks` has it. ## Idempotence and recovery

* Each step is one or more commits that leave the app working.  Step 1 keeps the arrays path that the page uses until step 3.  Step 3 keeps the memory path of a save.  A step can be reverted alone, from the last one back.
* Save files live only in `saves/`.  A run that stops leaves at most some save files, which the next start removes after an hour (D7), and Reset removes at once.  No session file changes.
* `e2e save` plants its sessions under new ids and removes them at its end; a run that stops leaves them, and the next run removes them first.
