# Stream from storage, M6: playback reads storage through the read-ahead buffer

## Purpose

This is the milestone plan for M6 of `plans/active/stream-from-storage.md` (the parent plan).  It gives more detail than the parent's M6 section, which stays the criteria.  After M6:

* The `Player` reads each lane through a trait in `engine` that gives the frames of a stem from a position.  A lane in memory (`Samples`) implements it, and so does a lane in a session file.  The player no longer holds the `Song`.
* For a lane in a session file, the audio callback copies frames only from a read-ahead buffer of a fixed size.  An async reader on the main thread keeps that buffer full in front of the play head and after the loop start (decision 0017).  If the buffer does not hold the frames, the lane plays silence and the buffer counts an underrun.
* A song shown from its session files plays from those files: the source lanes, the separated stems and the original lane.  A lane that has no complete session file (classic drums made on the page, the demo song, a song on the memory path) plays from memory, as today.
* No failure removes `mix.f32`, or any other session file, while the shown song plays from it.

M6 does not lower the page's memory yet.  The page still reads the session files back into `Samples` for the lanes, the spectrograms, classic drums and saves, until M7 and M8 (TD-54).  M6 adds the read-ahead buffer, at most 32 MiB.

Facts from outside the repo, checked on 2026-10-26:

* A `File` from `FileSystemFileHandle.getFile()` is a snapshot.  In Chrome, a read of it after the file changes fails with `NotReadableError`; a new `getFile()` gives the new contents ([MDN getFile](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/getFile), and M1's evidence above).
* `std::sync::Mutex::try_lock` never blocks ([docs.rs](https://doc.rust-lang.org/std/sync/struct.Mutex.html#method.try_lock)).  On `wasm32-unknown-unknown` with no threads, it always succeeds when nothing holds the lock.
* Symphonia converts a 16-bit sample to `f32` as `s / 32768` (`symphonia-core` 0.6.1, `src/audio/conv.rs`: `impl_convert!(i16, f32, s, s as f32 / 32_768.0)`).  Division by a power of two is exact, so a conversion written the same way gives the same bits.  Step 2 proves it with a test over all 65,536 values, not by this note.

Terms, besides the parent's and those of M3 to M5:

* Lane: one stem of the shown `Song`, as the `Player` plays it.  (The mix lane is drawn only; the player does not play it.)
* Stored lane: a lane that the player reads from a session file through the read-ahead buffer.  Memory lane: a lane that it reads from `Samples`.
* Lane file: the session file of a stored lane, with its format: f32 stereo (`mix.f32`, `decoded/<i>.f32`) or 16-bit stereo WAV (`stems/<name>.wav`), its data offset and its frames.
* Block: `BLOCK_FRAMES` (32,768) frames of every stored lane, read together.  Block `b` holds frames `b x BLOCK_FRAMES` up to the next block.
* Slot: one block's room in the read-ahead buffer.  Reader: the async task on the main thread that fills slots.
* Hold: the player plays silence and does not move, because the next run from a position that it has not played from yet is not in the buffer (D6).  A hold is not an underrun, and the callback does not wait in it (RT-1).

### Decisions of this milestone

* D1, the trait.  `engine::source::StemSource: Send + Sync` gives the frames of one lane:
  * `read(&self, from: u64, left: &mut [f32], right: &mut [f32])` fills both slices (the same length) with the frames from `from`.  Frames at or after the lane's end are 0.0.  Frames that the source does not hold now are 0.0, and the source counts an underrun (D5).  It never blocks, allocates or frees (RT-1).
  * `ready(&self, from: u64, frames: usize) -> bool`: whether `read` of that whole run gives real frames now (D6).  M8's save job asks it for each block before it reads, so a save never takes a silent gap for audio.
  * `hint(&self, hint: Hint)` stores atomics only, which the reader reads (D4).  `Hint::Reading { heard, read }` gives the player's own audible position (`Player::playhead()`, which trails the read position by the stretcher's latency) and the read position; never the target that D6 publishes while a seek holds.  The player gives it at the start of every `process`, also when paused.  `Hint::Seek(Option<u64>)` gives a seek that holds, or none.
  * `MemorySource` holds two `Samples` (clones share the buffer, MEM-1).  `read` copies, `ready` is always true, `hint` does nothing.  A function such as `memory_sources(&Song)` makes one for each stem, with no copy; a test pins the sharing (`Samples::shares`).
  * Names may change if the implementer finds better ones; the Decision log records it.
* D2, the player no longer holds the `Song`.  `Player::with_sources(sample_rate, frames, params, stretcher, cfg, sources: Vec<Arc<dyn StemSource>>)` takes one source for each lane, in the order of `params` (it panics on another count, as `with_config` does today).  `Player::with_config(song, ...)` keeps its signature: it makes the memory sources of `song` and calls `with_sources`.  `Player::song()` goes; `sample_rate()` and `frames()` take its place (`live.rs`, `pump_silent`, the tests).  So M7 can give the player its sources with no samples in memory.
  * `replacing_the_player_frees_the_previous_song` keeps its name and RT-1's purpose: it checks that the replaced player's sources are freed on the caller's thread, not in the callback (a test source that records its drop, or a `Weak` of a source).  `a_clone_shares_the_slot_without_keeping_its_song` changes the same way.
  * `read_mixed` keeps its arithmetic, bit for bit.  It finds the song frame of each input frame as today.  Then, for each lane with a gain, it reads each run of consecutive frames of `pos_buf` (and of `old_buf` for the loop crossfade) with one `read`, into two scratch pairs made in `with_sources`, and sums `vl x fin[k] + ol x fout[k]` and `v x g` in today's order.  A loop shorter than a run makes several runs; that is correct, only slower.
  * Before the change, in its own commit, `the_player_output_is_unchanged` records a 64-bit FNV-1a hash of `to_bits()` of the samples (in the test; no new crate) through tempo, chipmunk, a loop with a crossfade, a short loop, a loop set behind the head, a seek, a paused seek then Play, and mute and solo changes, at 44.1 kHz.  It hashes two things that use no libm function, so the hash is the same on macOS and on CI's Linux: the samples that the player pushes into a recording test stretcher (and the chipmunk output, which bypasses the stretcher), and the output through `Varispeed`.  wsola is not hashed, because its window calls `f32::cos` (platform libm).  The restructured player must give the same hashes.
* D3, the read-ahead buffer.  `engine::readahead::ReadAhead` is shared (`Arc`) by the stored sources of one song and the reader.
  * It holds `slots` slots.  Each slot is a `Mutex` around the block number it holds (or none) and one byte buffer for each stored lane, `BLOCK_FRAMES x bytes per frame` long: 8 for an f32 lane, 4 for a 16-bit lane.  The bytes are the file's bytes; the callback converts them (`f32::from_le_bytes`, or `i16::from_le_bytes` as `f32` divided by 32768.0, as symphonia does).
  * `ReadAhead::new(lanes, frames, params)` (and, for tests, a constructor that takes the two slot counts) makes every buffer at once, before the player is made, so the callback never allocates (RT-1).  Its size does not depend on the song's frames.  The slot counts: 16 slots for the run ahead and 8 for the loop (about 11.9 s and 5.9 s at tempo 1).  If 24 slots would pass `MAX_READ_AHEAD_BYTES` (32 MiB), the total is the most slots that fit, split 2 to 1 between the two (the loop's share rounded down), but at least 4 and 2.  Six 16-bit stems and an f32 original take 1 MiB a slot, so 24 MiB.  At the minimum of 6 slots, 32 MiB holds about 21 f32 lanes; a song whose stored lanes need more plays them from memory, and the Decision log records it if a test or scenario meets it.
  * Each slot also keeps its block number in an `AtomicU64`, which `fill` clears first and writes last.  The callback finds a block by that number among the slots (at most 24 compares), takes the slot with `try_lock` only, and checks the number again under the lock.  A slot that it cannot take counts as not held.  It never waits.
  * `StoredSource` is one lane of a `ReadAhead`: `read` copies the lane's frames from the slots that hold them, block by block.
  * The reader side, in `engine`, so native tests can drive it: `next_read(&self) -> Option<BlockRead>` gives the most wanted block that no slot holds and the slot to put it in (D4), or none.  `fill(&self, read: BlockRead, put: impl FnOnce(&mut [&mut [u8]]))` locks that slot, lets the caller write the bytes of every lane, and publishes the block number last.  A lane's bytes after the end of its file are zero.  `fail_lane(lane)` marks a lane failed (D7).  No lock is held across an `await`: the app reads the bytes first, then calls `fill`.
* D4, which blocks the reader wants (a pure function, `wanted_blocks`, with a native test).  `xf` is the player's crossfade (256 frames).  A loop `(s, e)` is "in force" when `loop_region` gives it and `s < e'`, with `e' = min(e, frames)` as `read_mixed` uses; its run of frames is `s` up to `min(e' + xf, frames)`, because the loop crossfade reads the `xf` frames after `e'` (`old_buf`).  In order of priority:
  1. If a seek holds (`Hint::Seek(Some(t))`): the blocks of the next run from `t` (D6).
  2. The run ahead, up to the ahead count of blocks.  It starts at the block of `heard` (so a chipmunk change that jumps back to the play head finds its block).  (A loop set behind the head is a held seek, D6, so item 1 lists its target.)  If a loop is in force and the run reaches `e'`, it goes on to `min(e' + xf, frames)`, then from `s`.
  3. The loop: from the block of `s`, up to the loop count of blocks, within its run.
  * Blocks past the song's end are not wanted.  A block is listed once, at its highest priority.
  * Only the first `slots` blocks of the list are kept.  The reader reads the first block of those that no slot holds.  It puts it in an empty slot, or else in the slot whose block is not kept, or else (none) reads nothing.  So a seek's blocks always get a slot at once, even with a loop set and the head outside it.
* D5, underruns.  A `read` of a run that the buffer does not hold, in full or in part, gives 0.0 for the missing frames, adds the missing frames to `missed_lane_frames` (frames times lanes), and marks the `process` as missed.  `underruns` counts the `process` calls with a miss (the player's `Hint::Reading` at the start of each `process` clears the mark).  Both are atomics on `ReadAhead`.  A memory lane never underruns.  A muted lane is not read, so it does not count.  A failed lane (D7) counts no underrun.
* D6, seeks, holds and the play head.
  * The next run from a position `p` is the frames that the player reads next: from `p` to `min(p + BLOCK_FRAMES, frames)`; if a loop is in force and `s <= p < e'` (`e' = min(e, frames)`, as `read_mixed` uses), only to `min(p + BLOCK_FRAMES, e' + xf, frames)`.  If that run reaches `e'`, the next run also takes in the loop's first frames, from `s` to `min(s + BLOCK_FRAMES, e' + xf)`.  `ready`, item 1 of D4 and the hold below all use this same run, so a run that the player asks for is always one that the reader reads.
  * While playing, a seek to a target whose next run is not `ready` does not fade or jump yet.  The player keeps playing from its position, and gives `Hint::Seek(Some(target))`.  Each `process` checks again.  When the run is ready, the seek fades out and jumps as today, and the hint is cleared.  A newer seek replaces the held one.  So the old position plays until the new block arrives (the parent's acceptance).  While a seek holds, the player publishes the target as `playhead`, so the head shown does not jump back.
  * When paused, a seek jumps at once, as today.
  * After any jump (a seek, a chipmunk change, a new player), the player has not yet played from its position.  If it plays and the next run from that position is not ready, it holds: it renders silence, does not move, and adds the frames to `held_frames`.  It starts as soon as the run is ready.  A memory lane is always ready, so a song of memory lanes never holds.  (A hold is the player's choice to play silence; the callback itself never waits, RT-1.)
  * A loop set behind the head: the player keeps the loop that it plays (its own copy), and takes the loop of `SharedParams` at the start of each `process`.  If that loop is new or has changed, and the read position is at or after `e'`, the next read would wrap to `dsp::wrap_loop(read, s, e')`, a position the player has not played from.  If that position's next run is ready, the player takes the new loop and wraps as today, with the loop crossfade, so the memory path does not change.  If not, the change is a held seek to that position: the player keeps its old loop (or none), plays on, gives `Hint::Seek(Some(target))`, and when the run is ready, fades out, jumps and takes the new loop.  A wrap at `e'` of an unchanged loop (the read position reached `e'` by reading, also when a read ends exactly at `e'`) is not a jump: the loop's run is in the buffer (D4), and if it is not, the lane underruns (D5).
  * A pause turns a held seek into a paused seek: it jumps at once.  The stop at the song's end (`player.rs`, `head >= frames`) uses the player's own head, not the published target.  The player does not stop at the song's end while a seek holds or fades out toward its target: silence plays past the end until it jumps.
* D7, read failures.  The reader reads each lane on its own promise (`Promise.allSettled`, or one promise for each lane), so one bad lane does not lose the others' block.  If a read of a lane fails, the reader gets the file again (`getFile`) and reads that lane's range once more.  If that fails too, it calls `fail_lane`, and fills the block with the failed lane's bytes as zero.  A failed lane plays silence from then on, counts no underrun, and never makes `ready` false.  If every stored lane has failed, every position is ready, so the memory lanes (classic drums) still play and the head still moves.  `failed_lanes` goes up, the page logs `playback: lane <name> failed: <error>` once, and the status line says "Could not read the <name> lane from browser storage; it plays silent."  The other lanes go on.  A new `getFile` after a move of the file (for example `keep_stored_stems` during a new separation of the shown song) reads the new file, and the song with the new stems is shown soon after; the Decision log records this.
* D8, which lanes are stored.  Each function that reads a lane from a session file gives its lane file with it: `read_back` for each source, `read_stem` (so `stems_of`) for each stem, and the read of `separation_stored`.  `StemApp::open_song` and `load_song` take a list of lane files aligned with `song.stems` (`None` for a memory lane), so no caller keeps a map that can drift from the stems shown.  A lane is stored only if its file was complete when it was read: its size is the size of the song's frames (f32), or a WAV header of 16-bit stereo PCM at 44,100 Hz whose data chunk holds at least the song's frames less one (frames past the song's end are not read, and a missing last frame reads as 0.0, as `read_stem` pads).  Else it is a memory lane.
  * A source lane of a complete session (D2 of M5): its `source_file` (`mix.f32` for the source in the mix of a song of one source, else `decoded/<i>.f32`).
  * A stem read from `stems/<stem_file(name)>`.  A stem read from a `.part` path (`not_kept` in `separation_stored`) is a memory lane, because the next separation writes that path.
  * The "original" lane of `with_original`: the lane file of the source lane that `original_lane` takes (one source), or `mix.f32` if the session has a usable mix of the song's frames (several sources).  For several sources, `mix.f32` equals `mix_of_sources` bit for bit (D5 of M5 and M5's step 3 Decision log: the second pass sums at volume 1 and clamps as `dsp::mix` does).  `with_original` and its callers carry the list.
  * Classic drums made on the page (`add_stem` removes any lane of the same name from the stems and from the list together, then appends `None`; a native test has a "classic drums" source that is not the last lane), the demo song, a song decoded on the page (`load_files`, the memory path of D9 of M5), the stems that `apply_inbox` takes from `stems_for_opening`, and the stems of a memory-path separation are memory lanes.  M7 adds the classic-drums file.
  * The names and formats come from a pure function in `app/src/store_meta.rs` with a native test.  The WAV header parse is a pure function with a native test.
* D9, the reader on the page (`app/src/playback.rs`, web only).
  * `load_song` first drops the old player and stops the old reader (as it frees `mix_follower`), so two read-ahead buffers never live at once.  Then, if the song has a stored lane, it makes the `ReadAhead` and the sources, the player, and starts the reader with `spawn_local`.
  * The reader holds a `Weak<ReadAhead>`, and stops when it cannot upgrade it or when its song's serial is no longer shown.  It holds no strong reference across an `await`.  It gets each lane's `File` once (`getFile`) at its start.
  * Each turn: `next_read`; if there is a block, it reads that block's byte range of every stored lane that has not failed (D7), as M1's spike reads with `Blob.slice(...).arrayBuffer()`, then copies each `ArrayBuffer` into the start of the lane's slot bytes with `Uint8Array::copy_to` inside `fill`, and zeroes the rest (a short last block, a stem one frame short), so a slot used again keeps no old bytes.  It never reads more than one block of a lane at a time.  If there is no block to read, it waits 10 ms (`setTimeout`) and looks again.  So a seek starts a read within one callback (about 46 ms, when the callback gives `Hint::Seek`) and the 10 ms poll.
  * It records the time of each block read.  The page logs a `playback:` line every 2 s while playing, after the `audio stats:` line: `playback: lanes from storage S of T, read-ahead R MiB, underruns U (callbacks), missed lane frames F, held H frames, failed lanes L, lanes read K, reads N, read p50 A ms, p99 B ms`.  K counts the stored lanes that the player read since the last line: the lanes that play, not muted.  `xtask e2e` parses it with a pure function.
* D10, no failure removes a file that playback reads.  `store` keeps a set of protected sessions.  A session is protected from the moment an open reads its first lane file (a guard that the open holds until `apply_inbox` shows the song or the open ends) and while the shown song has a stored lane of it (`store::set_playing`, set by `load_song`).
  * `forget_mix` removes nothing for a protected session.  It checks inside its `meta` lock, logs `store: the mix of session <id> is kept while playback reads it`, records the removal as deferred, and returns `Ok`.  When the session stops being protected and no separation or mix write names it (`store::mix_in_use`), the page runs the deferred removal (again through `forget_mix`, which now checks `mix_in_use` itself).  A separation that posts the session's mix cancels the deferral, because the worker reads that mix.  So D6 of M4 still holds: a mix that the worker could not use goes once no song plays from it, and the next Separate writes it again.  Both callers (`separation_unstored`, `decode_session`) keep their other behaviour.  A Separate again of the shown song, while it is protected, posts the same mix: the memory path takes a short song at once (D4 of M3), and for a song too long for it, the status line of `separation_unstored` says: "Browser storage failed (...).  To try again, open another song, then open this one again and press Separate."  Opening another song ends the protection, so the mix goes, and the next open decodes it again.
  * The Storage menu offers no "Forget" for a protected session (the shown song that plays from it, or a session being opened), with the hover text "This song plays from browser storage; open another song first".  `forget_enabled` takes the protected session, with a native test.
  * The parent's M6 bullet says "before playback reads `mix.f32`, no failure removes it".  This plan reads it as: a failure never removes a session file while the shown song plays from it or an open reads it, and D6 of M4 and D8 of M5 hold once it does not.  The Decision log records it.

## Idempotence and recovery

* Each step is one or more commits that pass every check.  Steps 1 and 2 change only `engine` (and the callers of `Player::song()`); the app still plays memory lanes until step 3.  A step can be reverted alone, from the newest back.
