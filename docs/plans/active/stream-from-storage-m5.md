# Stream from storage, M5: a song decodes from storage into storage

## Purpose

This is the milestone plan for M5 of `plans/active/stream-from-storage.md` (the parent plan).  It gives more detail than the parent's M5 section, which stays the criteria.  After M5:

* The page never holds the encoded source of a song that it keeps in browser storage.  It saves a chosen file to OPFS as a `Blob`, as today, and does not read its bytes.
* A new page-side worker, the decode worker (decision 0019), reads the stored source in blocks with sync reads.  It decodes, converts to 44.1 kHz and writes the session files and the overviews in blocks.  Its memory does not grow with the song.
* A song of one source decodes into `sessions/<id>/mix.f32`, M4's mix file, with M4's `mix` line.  So Separate writes no second mix file.  A song of several sources gets one session file for each source, and `mix.f32` made from them in blocks.
* A restored session decodes its stored sources in the same way, or uses its session files if they are complete.

M5 does not close TD-54.  After the decode, the page still reads the session files back into memory to play the song and draw its lanes, until M6 and M7 (the orchestrator's decision of 2026-10-26).  The page also still reads the stem WAVs of a restored session whole, until M7.

## Context and orientation

The state at the start of M5, on 2026-10-26, at commit `83dfdde` on the branch `iphone-crashes-2026-10-25`.  The parent plan's "The code today" and "Terms", and the M3 and M4 plans (their D1 to D10 and D1 to D8), apply.  These parts concern M5:

* `engine/src/decode.rs`: `decode_bytes` and `decode_path` decode a whole file into `Audio` (one `Vec<f32>` per channel, at the file's rate).  `open` probes the file and computes the reservation.  `decode_into_reservation` decodes packet by packet and grows the channels with `append`.  `MAX_DECODED_BYTES` (decision 0013) stops a file over 1 GiB of `f32` samples, with mono counted as two channels.  The tests use a peak allocator (`PeakAllocator`), FLAC files from `engine/src/test_flac.rs` and hand-made MP3 frames (`mp3_frame`, `quiet_start_mp3`).
* `engine/src/resample.rs`: `to_rate(x, from, to)` converts a whole channel with a polyphase filter (`Filter::apply`).  Output `i` is a dot product of `2 x half` input samples around `Position::at`, with zeros outside the input.  Its length is `ceil(len x phases / step)`.
* `engine/src/song.rs`: `Song::from_audio` sorts the sources by `rank`, takes at most two channels, converts the rate, makes a mono source stereo (both sides share one `Samples`) and pads every source with silence to the longest.  `Song::load_files` skips the names in `NOT_STEMS` (`mix`, `original`, `truth`), after `stem_name`.
* `app/src/lib.rs`: `handle_drops` and `pick_song` read every chosen file whole (`bytes_async`, `picker::read`), then `load_and_keep` decodes them on the main thread (`Song::load_files`) and saves them (`store::save_sources`).  It logs `song kept in browser storage as session <id>`, which `e2e smoke`, `e2e separate` and `e2e memory-budget` wait for.  `StemApp::new` restores `sessions/current` (`store::restore`); the Storage menu opens a session with `store::restore_id`.  `load_song` builds the lanes with `lane_columns` (`COLUMNS` = 4096 columns of `dsp::peaks`, and a scale from `dsp::biggest`), and the mix lane from `mix_of_sources`.  `original_lane` and `with_original` give the original lane.
* `app/src/store.rs`: `save_sources` writes each chosen `Blob` to `sessions/<id>/src/<i>.<ext>` and writes `meta`.  `restore_id` and `rebuild` read the sources whole (`read`, an `#[expect]` of MEM-1) and decode them with `Song::load_files`; `read_stem` reads a stem WAV whole.  `SAVING`, `saving`, `SaveHeld` and `settled` order the saves of a session; `WRITES` and `CLOSED` let a reset wait.  `stored_mix_frames`, `write_mix`, `forget_mix` and `MIX_BLOCK_FRAMES` are M4's.  `app/src/store_meta.rs`: `Meta`, `MIX_FORMAT` (`f32le-1`).
* `app/src/separator.rs`: how the page starts the stem worker (`WORKER_URL`, `Worker::new_with_options`), takes its replies into `Event`s, and logs `page_wasm_mb`.  The app's browser tests make a `Separator` whose script does not exist, spy on its posts (`spy_on_post`) and give it replies (`deliver`).
* `app/index.html` builds `stem-worker` with Trunk (`data-type="worker"`, `data-loader-shim`).  `app/src/reset.rs` lists its three files (`WORKER_FILES`) for "Reset…", and a test checks them against `app/index.html`.  `xtask/src/publish.rs` lists the files of a build.
* LAYER-1 (`docs/invariants.md`), the layers table in `docs/ARCHITECTURE.md`, and `WEB_APP`, `LAYERS` and the LAYER-1 tests in `xtask/src/rules.rs`.  DEPS-1 and `THIRD-PARTY.md` (its two `cargo tree` commands name `app` and `stem-worker`).  MEM-1's clippy lint is one `clippy.toml` in each crate, with a canary test (decision 0008).
* `xtask/src/web_test.rs` runs the browser tests of `app`, `stem-worker` and `stem-protocol`.  `.github/workflows/ci.yml` runs clippy for wasm32 on a list of crates, `web-test`, and `e2e smoke`, `audio-resume`, `storage` and `flac` in Chrome.
* `xtask/src/e2e.rs`: `memory_budget` drops a WAV of 1 and 4 minutes (`long_song`), separates it, and checks the growth of the page and the stem worker during the separation (`page_growth`, `worker_growth`, `growth_check`, `MAX_GROWTH_MB` = 4).  `memory_peak` takes the largest `page wasm`, `worker wasm` and `GPU buffers live` value of the `memory: ...` lines.

Facts from outside the repo, checked on 2026-10-26:

* `FileReaderSync` and `FileSystemSyncAccessHandle` exist in dedicated workers only ([MDN FileReaderSync](https://developer.mozilla.org/en-US/docs/Web/API/FileReaderSync), [MDN FileSystemSyncAccessHandle](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemSyncAccessHandle)).  The stem worker already uses both (`blob_range`, M3's stem writer).
* Symphonia reads a `MediaSource`, which is `Read + Seek + Send + Sync` with `is_seekable` and `byte_len` ([docs.rs](https://docs.rs/symphonia-core/latest/symphonia_core/io/trait.MediaSource.html); symphonia-core 0.6.1, `src/io/mod.rs`).  A Rust value that holds a `Blob`, a `File` or a `FileReaderSync` is not `Send` or `Sync`, so the worker's source cannot hold one (D7a).  The format reader gives one packet at a time, so a decode in blocks needs no change to symphonia.
* eframe 0.36.2 reads a dropped file's bytes only when `bytes_async` is called; `web_file` gives the browser's `File` (`egui::DroppedFile`).

Terms, besides the parent's, M3's and M4's:

* Decode worker: the new crate's Web Worker (decision 0019).  The stem worker is `stem-worker`.
* Source: a file of the song that `Song::load_files` keeps (not `mix`, `original` or `truth`).  A source is in the mix unless its name is in `DERIVED` (for example a re-dropped `classic drums.wav`), as `mix_of_sources` and `put_mix_blocks` count it.
* Song of one source: a song for which `original_lane` gives a source lane: one source in the mix.  It can also have derived sources.  Every other song is a song of several sources.
* Source file: `sessions/<id>/decoded/<i>.f32`, one decoded source at 44.1 kHz, where `<i>` is the index of its `src/<i>.<ext>` file.
* Overview file: `sessions/<id>/overviews/<i>.f32` for source `<i>`, or `overviews/mix.f32` for the mix lane: the columns of a lane's waveform.
* Complete session: a session whose `meta` has a usable `decoded` line (D2).

## Plan of work

### How the team works

The team leader wrote this plan, has it reviewed, runs the review rounds and commits Progress.  One implementer (a `general-purpose` subagent) does steps 1 to 5 and the review fixes.  It starts no other agent.  Before each commit it runs the checks of GIT-2 (`CLAUDE.md`, Commands), commits signed (`git commit -S`) with the attribution lines that the team leader gives, and does not push.

Each commit leaves the docs true (DOC-1).  A message changes in one commit with its encoder, its decoder and their tests (PROTO-1).  Write each test first and see it fail for the right reason, then write the code.  A workaround or a known gap gets a `docs/tech-debt.md` entry in the same commit.

### Decisions of this milestone

* D1, the session files.  Every session file of a song holds the song's frames: raw 32-bit float, little-endian, interleaved stereo, no header, at 44.1 kHz, as M4's mix file (format `f32le-1`).  A mono source has the same samples on both sides.  A source has at most two channels, as `Song::from_audio` takes.
  * A song of one source: `mix.f32` is the source file of the source in the mix (decision 0016), unclamped, as `original_lane` gives it.  A derived source, if any, gets `decoded/<i>.f32`.
  * A song of several sources: `decoded/<i>.f32` for each source, padded with silence to the longest, and `mix.f32`, which is `dsp::mix_range` of the sources in the mix at volume 1 (the samples of `mix_of_sources`).
  * A song with no source in the mix (only derived sources, such as a drop of `classic drums.wav` alone) gets a `mix.f32` of silence, as `mix_of_sources` gives.  A drop with no source at all (only `mix.wav`, say) fails on the page, before any post, with today's "no stems to load".
  * Every file of D1, `mix.f32` included, is padded to the song's frames, which are the longest source's, derived sources included (as `Song::from_audio` pads).
  * A test covers a song of `drums.wav` and `classic drums.wav`, with `classic drums` the longer: the mix is `drums` alone, unclamped, padded to the song's frames, and `classic drums` has its own source file.
  * Overviews: `overviews/<i>.f32` for each source lane, and `overviews/mix.f32` for the mix lane (`mix_of_sources`, which `dsp::mix` clamps).  An overview file holds the columns of `lane_columns`: for each column, its minimum and then its maximum, as 32-bit little-endian floats.  The scale is not stored; it comes from the columns.  Each overview has a fixed size (at most 32 KiB), so it does not grow with the song.
  * The samples are those of `decode_bytes` and `Song::from_audio` today, bit for bit (D4).  So the format tag stays `f32le-1`, and an `mix.f32` of M4 is still usable.
  * The tag `f32le-1` of the `decoded` line (D2) covers the source files and the overview layout together.  A later change to either takes a new tag, so the session decodes again.
* D2, `meta`.  The page is the only writer of `meta`.  When the files of D1 are complete, the page writes the line `decoded<TAB><frames><TAB>f32le-1`, and the `mix` line of M4 if it moved a new `mix.f32` into place.  A session is complete when its `decoded` line has the format `f32le-1`, and every file of D1 has its size: `8 x frames` for `mix.f32` and each `decoded/<i>.f32`, and `8 x columns` for each overview, with `columns` = `ceil(frames / ceil(frames / COLUMNS))`.  `frames` is at least 1, because a source that decodes to no audio is `undecodable` (as `decode_bytes` refuses it today).  The `decoded` line, or one line for each source, also records each source's channels (1 or 2), for D10.  `Meta::parse` ignores lines it does not know, so an older build ignores the line.  Before the page asks for a decode, it removes the `decoded` line.
* D3, the decode worker crate.  Directory `decoder/`, package `decode-worker`, in the Shells layer, with the row `decode-worker | dsp, engine, stem-protocol`.  It takes `engine` with `default-features = false` (no stretcher, no `cpal`).  Its other dependencies are crates that `app` or `stem-worker` already take, at the same versions (`wasm-bindgen`, `wasm-bindgen-futures`, `js-sys`, `web-sys`, `console_error_panic_hook`).  So DEPS-1 asks only for the `THIRD-PARTY.md` commands to name it.  Trunk builds it from `app/index.html` as it builds `stem-worker`, with a loader shim: `decode-worker_loader.js`, `decode-worker.js` and `decode-worker_bg.wasm`.  It has its own `clippy.toml` of MEM-1 with a canary test, as `stem-worker` has.  Unlike `stem-worker`, it takes `engine`, `dsp` and `stem-protocol` as normal dependencies on every target, and keeps its pass logic in code that compiles natively, so `cargo test -p decode-worker` runs the native tests of step 3.  Only the browser glue is for wasm32.
* D4, the engine API.  `engine` gets three block parts, each natively tested against the whole version, bit for bit:
  * `engine::decode::Decoder`: opens a `MediaSource` as `open` does, and gives the next packet's planar `f32` samples on each call.  It keeps the checks of `MAX_DECODED_BYTES` (decision 0013): it stops with the same error when the frames so far pass the limit.  `decode_bytes` and `decode_path` keep their behaviour, their reservation and their tests, built on `Decoder`.
  * `engine::resample::Resampler`: takes input in blocks of any size and gives the output of `to_rate` on the whole input, bit for bit, with the same length.  At the same rate it passes the input through.  It holds at most one filter window of input, not the song.
  * A stereo sink trait (for example `engine::song::FrameSink` with `put(&mut self, left: &[f32], right: &[f32])`) and a function that decodes one source into a sink at 44.1 kHz: at most two channels, mono to both sides, and the rate converted in blocks (for example `engine::song::decode_source`).  `Song::from_audio` keeps its behaviour, and a memory sink gives the samples of `Song::from_audio` for one source.
  * Names: the block decode of one source must not clash with the private `decode::decode_source` (for example `engine::song::decode_into`).
  * `engine::overview`: `lane_columns` moves from `app` to `engine`, with a block builder that gives the same columns and scale from blocks of any size, when it knows the frames first.  `app`'s `load_song` calls it.  The block builder is for the decode worker and M7.
* D5, the overview is made in a second pass.  The columns of `lane_columns` depend on the song's frames.  An MP3 states only an estimate of its frames, and the frames of a song of several sources are the longest source's.  So the decode worker makes the overviews after the decode, in a pass that reads the session files in blocks.  This is the "same pass" of the parent's M5 section in what it asks: no song-length memory, and no whole read.  The same pass pads every file of D1 to the song's frames.  For a song of several sources it also writes `mix.f32`.  It makes every overview.
* D6, the messages (PROTO-1).  New messages in `stem-protocol`, in their own module (for example `stem_protocol::decode`), with their own `kind` constants, one encoder and one decoder each, and round-trip tests in `protocol/tests/web.rs`.  No samples cross, so there is nothing to transfer (MEM-2).
  * Request `decode`: the session folder (`sessions/<id>`), the sources in the order of `Song::from_audio` (each its stored file `src/<i>.<ext>`, its index `<i>`, its extension, and `in_mix`: false for a name in `DERIVED`), and `mix_frames`, the frames of a usable `mix.f32` of D1 of M4, if the page found one.  The page computes the order and `in_mix` with `engine` functions that `Song::load_files` also uses (make `rank` and the `NOT_STEMS` test public in `engine::song`).  A missing or wrong field is a decode error, not a default (TD-16).
  * Replies: `decode-alive`, which the worker sends once its wasm has started and it listens, as the stem worker sends `alive`; `decoded` with the song's frames, whether the worker wrote a new mix, and the channels (1 or 2) of each source; `undecodable` with a text, when a source cannot be decoded (a format error, a file too long); `unstored` with a text, when browser storage fails (a read or a write); and log lines.  Each request ends with exactly one of `decoded`, `undecodable` and `unstored`.  A missing channel count is a decode error (TD-16).
  * The page queues every `decode` post until `decode-alive` arrives, as `separator.rs` holds `Init` until `Alive`, so a startup restore is never lost.  A test: a post made before `alive` goes out after `deliver(alive)`.  The `kind` strings differ from the stem worker's (for example `decode-unstored` and `decode-log`, not `unstored` and `log`).
* D7, the files the worker writes.  The worker writes each file of D1 as `<name>.decode.part` (so `mix.f32.decode.part`, never M4's `mix.f32.part`) through one `FileSystemSyncAccessHandle`, in blocks of 131,072 frames (1 MiB), each a new whole `Uint8Array` (MEM-5).  It closes each handle before it replies, because a move fails while a handle is open.  It reads each source, and an existing `mix.f32`, in blocks with `getFile` and `FileReaderSync` (as `blob_range` does), never through a sync access handle, so a running separation's reads see no lock.  It reads its own `.part` files back for the second pass (D5) in blocks of at most 1 MiB.  It removes its `.part` files when it ends with `undecodable` or `unstored`.  On `decoded`, the page, inside `SAVING`, moves each `.part` file onto its name (as M3's `keep_stored_stems` does), and writes the lines of D2.  For a new mix, it first removes the `mix` line, then moves the file, then writes the `mix` line.  If a move or the `meta` write fails, the session stays incomplete, and the page treats it as `unstored` (D9).
* D7a, a read failure is never the end of a file.  `decode_into_reservation` takes an `IoError` of kind `UnexpectedEof` as the end, and a failure in the probe gives "unsupported or unrecognised format".  The worker's `MediaSource` holds only numbers (a handle, a position, `byte_len`).  The `File` stays in a table on the JS side, and the source reads through an inline-JS function such as `read_range(handle, start, end)`.  Do not write `unsafe impl Send` or `Sync`.  The source never returns `Ok(0)` before `byte_len`, maps a failed read to an error of another kind (for example `Other`), and records the failure.  The worker checks that record first, and replies `unstored`, not `decoded` with a short song or `undecodable`.  Tests, native, with a source that fails: a read that fails in the probe, and one that fails in the middle, each end with `unstored`.
* D8, the mix is never written again while it is usable.  When the page sends `mix_frames`, the worker writes no mix.  For a song of one source it then decodes only its derived sources, if any, and pads them to `mix_frames`; it ends with `unstored` if one is longer.  The frames are `mix_frames`, and it makes the overviews from `mix.f32` and the derived files.  In that pass it records the channels of the source in the mix as 1 when every frame of `mix.f32` has its left equal to its right, bit for bit, and else 2.  So it reads no source, and a mono M4 mix still reads back shared (D10).  A test covers a mono M4 mix.  For a song of several sources it decodes the sources, and checks that their frames equal `mix_frames`; if not, it ends with `unstored`.  The page then takes the memory path of D9, and removes the `mix` line and `mix.f32` (`forget_mix`) only if no separation names the session, so the next open decodes again.  The page also checks again at D7, inside `SAVING`.  It keeps the mix there if the session has a usable mix of the song's frames now (`usable_mix_frames`; decision log, review round 2).  It also keeps it if a separation or a mix write (`JobStage::WritingMix`) names the session.  Then it removes `mix.f32.decode.part`.  Separate stays disabled while a decode of the shown session runs.  So no step of M5 writes a `mix.f32` that a separation may read (TD-55): a separation on the storage path starts only with a usable mix, and the page keeps the mix usable until the separation ends.  A test of the order that the menu allows (it opens a session during a job): Separate is pressed on a session with no usable mix, then the same session opens again from the Storage menu, and its restore reads `meta` before `write_mix` holds the session.  D7 removes `mix.f32.decode.part`, and `mix.f32` does not change.
* D8a, no wait on the page's own guard.  `settled`, and so `stored_mix_frames`, `restore_id` and `forget`, wait while `SAVING` holds a session.  So D7 and `complete_frames` read `meta` through a helper that does not call `settled`, and no function that calls `settled` runs for a session while its decode guard (D9) is held.  A test: D7's keep path, with a planted `mix` line, completes within a timeout.
* D9, the paths of an open, on the page:
  * The page saves the chosen files with `store::save_sources`, as `Blob`s, before it reads anything.  `save_sources` takes `SONG_RATE`, because the page has no decoded song yet.  If that fails (no OPFS, no space), the page reads the files and decodes them on the main thread, as today.  This is the memory path of decision 0015.
  * With a session, the page posts `decode`.  On `decoded` it does D7, then reads the session files back in blocks (D10) and shows the song.  On `undecodable` for a new song, it shows the error, as today's "Could not load: ...", and forgets the new session.  The new session becomes current only once its song opens (decision log, review round 2).  If the song does not open, through the worker or on the page, the page forgets the session.  Then `sessions/current` does not change.  On `unstored` it reads the stored sources and decodes them on the main thread, as today, keeps the session, and its status line says that browser storage failed.  If the decode worker cannot start, or stops (an `error` event), the page takes that path too, terminates the worker, and starts a new one for the next open.
  * Each decode has one guard on the page that holds a count in `SAVING` and in `WRITES`, from the post to the end of D7.  So Forget and `store::close` wait for it.  The reply, an `error` event and a terminate each drop the guard.  The page releases the guard before it calls `forget`, which waits on `settled`.  "Reset…" terminates the decode worker and drops its guard first, then calls `store::close`, so a reset never waits for a long decode, and never waits for ever on a worker that cannot reply.  The page posts no decode after `CLOSED`.  A test: a reset during a decode completes.
  * The decode worker runs one request at a time, in the order sent; each reply belongs to the oldest decode not yet ended.  If another song opens before a decode ends, the page completes the session (D7) but does not show the older song, as the inbox and `opens` do today.
* D10, the read-back after the decode (until M6 and M7).  The page reads each session file in blocks of 1 MiB (`Blob.slice` and `arrayBuffer`), into two channels reserved at the song's frames.  It never holds a whole file's bytes.  It builds the `Song` as `Song::from_audio` names and orders it.  A song of one source reads `mix.f32` for its source in the mix; every other source reads its `decoded/<i>.f32`.  This read stays until M6 and M7 (TD-54).  A mono source (D2 records its channels) reads back its left side only, and shares it as the right side, as `Song::from_audio` does today (MEM-1); `a_decoded_song_is_read_back_and_shown` checks `Samples::shares`.  If a read-back of a complete session fails, the page removes the `decoded` line and asks for a decode (D9).
* D11, a restored session.  `restore_id` reads `meta`.  If the session is complete (D2), the page reads it back (D10), with no decode.  Else it asks the decode worker (D9), with the `mix_frames` of a usable mix (D8).  On `undecodable` in a restore, the page keeps the session, with its stems, and shows today's "Could not restore the stored song: ..." (or "could not open the stored song") text.  On `unstored` it falls back to today's `rebuild`.  The page logs `decoder: read back a complete session` when it restores with no decode, and `decoder: decoding on the page` when it takes the memory path, so e2e checks can tell the paths apart.  The stem WAVs and the original lane follow as today (`read_stem`, `with_original`); `read_stem` still reads a WAV whole until M7.  The page no longer reads a source whole, except on the memory path of D9.
* D12, the memory lines and the other log lines.  The page logs `decoder: memory: page wasm N MB as the open starts` in the drop and pick handlers, before any read or save, and `decoder: memory: page wasm N MB as the decode ends` after D7 and before the read-back.  The decode worker makes its fixed working set once, when it starts: the read buffer, the write block and its staging, and the second pass's read block, each at most 1 MiB.  It sets symphonia's `MediaSourceStream` buffer to at most 1 MiB.  It logs `decoder: memory: decoder wasm N MB at the decode's start` after that warm-up and before it opens a source, and `decoder: memory: decoder wasm N MB at the decode's end` before its last reply.  The words `decoder wasm` differ from `worker wasm`, so `memory_peak` does not take the decode worker's lines as the stem worker's.  The page logs `song kept in browser storage as session <id>` when the song is shown from its session files, so the e2e scenarios that wait for it still wait for a shown song.  It logs the line only after `sessions/current` names the session, so a scenario that reloads at the line restores that song (review round 3, finding 3-1).  On `decoded` it logs `song: opened at 44100 Hz in N s (F frames)` with the reply's frames, which `e2e separate` checks, and a restore keeps its status lines (`Restored "<name>" from this browser`), which `e2e storage` waits for.  Check every line that `xtask/src/e2e.rs` waits for or checks, and keep each one true.

### Step 1: the block parts in `engine`

* D4.  Update the module docs of `engine/src/decode.rs`, `engine/src/resample.rs` and `engine/src/song.rs`.
* An MP3 with sound in it for the tests: `engine` may take `rusty_mp3 = "=1.0.0"` as a dev-dependency (already pinned in `worker/Cargo.toml`, DEPS-1).  If its output does not decode, use the hand-made frames of today's tests and record why.
* Tests, native (`cargo test -p engine`):
  * `a_block_decode_gives_the_whole_decode`: a WAV (16-bit and float), a FLAC and an MP3, mono and stereo.  A memory sink gives the samples of `decode_bytes` and `Song::from_audio`, bit for bit; so does a sink that records blocks.
  * `the_block_resampler_gives_to_rate_exactly`: from 48, 22.05, 8 and 96 kHz to 44.1 kHz, with blocks of 1, 7, 1,000 and 131,072 frames and lengths that are not a multiple of the block.  The output equals `to_rate` bit for bit, with the same length.
  * `a_block_decode_keeps_its_memory_flat` (in the test module of `engine/src/decode.rs`, which owns `PeakAllocator`): with `PeakAllocator`, the peak above the start for a decode into a sink that keeps nothing differs by less than 1 MiB between a 2-second and a 60-second WAV, FLAC and MP3, at 44.1 and 48 kHz.  A control: `decode_bytes` of the long file peaks more than that bound above the short one.
  * `the_block_overview_gives_lane_columns`: for frames of 1, 4,095, 4,096, 4,097 and 1,000,003, and blocks of any size, the columns and the scale equal `lane_columns`.
  * `the_decode_limit_stops_a_block_decode`: a file over the limit gives the error of `too_long` from `Decoder` too.

## Idempotence and recovery

* Each step is one or more commits that pass every check.  A step can be reverted alone, from the newest back.  Step 2 alone adds a crate that the page does not yet use.
* A decode that stops leaves `.part` files, which nothing reads, and no `decoded` line.  The next open of the session decodes again and replaces them.  Forget removes them with the session.
* A session of M4 or older has no `decoded` line.  Its first open in M5 decodes it, and keeps a usable `mix.f32` (D8).
* If the decode worker fails, the page decodes on the main thread as today (D9), so an open never depends on the new worker alone.
